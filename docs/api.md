# Versioned REST and OpenAPI contracts

**Status:** Phase 1 implementation of
[issue #34](https://github.com/ForkbombEu/credimi-attestbook/issues/34). This document
describes the public product API that the running server actually exposes, the error
envelope every route shares, the URL versioning and idempotency policies, and how the
OpenAPI 3.1 document is generated and validated in CI. It is not a TS11 catalogue API and
makes no standards-conformance claim.

**Authoritative spec:** [`docs/specification.md`](specification.md) §13, §15 and §16.
**Architecture:** [`docs/architecture.md`](architecture.md) §5 (HTTP/API boundary) and §6
(authorization and provider ownership).
**Services exposed:** [`docs/registry.md`](registry.md), [`docs/import.md`](import.md) and
[`docs/validation.md`](validation.md).
**Decisions:** [`docs/implementation-plan.md`](implementation-plan.md) D-10 (provisional
bearer authentication), D-14 (Hono + Zod/OpenAPI layer) and D-15 (CI jobs, including the
`openapi` job introduced by this slice).

## 1. Scope and boundaries

Implemented and exposed by this slice:

- public catalogue reads of rulebooks, attestation types, schema references and versions;
- the public provider projection used by the catalog UI (added by
  [issue #36](https://github.com/ForkbombEu/credimi-attestbook/issues/36));
- exact snapshot bytes and the content digest of one version;
- authenticated create of a draft rulebook (including rulebook-level schema references),
  create of a draft version and publication;
- public read, authenticated full replacement and public live validation of a draft working
  copy (added by [issue #40](https://github.com/ForkbombEu/credimi-attestbook/issues/40));
- deterministic version comparison, authenticated draft-snapshot refresh and public
  publication-readiness checks (added by
  [issue #41](https://github.com/ForkbombEu/credimi-attestbook/issues/41));
- stable export of published/historical artifacts and a public publication export manifest
  with the artifact digest, bounded provenance and an explicit signature boundary (added by
  [issue #42](https://github.com/ForkbombEu/credimi-attestbook/issues/42));
- authenticated import preview and import of URL/JSON sources;
- authenticated issuer metadata discovery and candidate rulebook association (added by
  [issue #43](https://github.com/ForkbombEu/credimi-attestbook/issues/43));
- the optional environment-configured administrator browser login and its opaque, expiring
  server-side session (added by
  [issue #88](https://github.com/ForkbombEu/credimi-attestbook/issues/88));
- public rulebook-driven unsigned issuer fixture generation (added by
  [issue #44](https://github.com/ForkbombEu/credimi-attestbook/issues/44), hosted-schema
  grounding added by [issue #102](https://github.com/ForkbombEu/credimi-attestbook/issues/102));
- structural credential validation against a pinned rulebook version;
- reproducible continuous-conformance evidence with a stable content-addressed result
  reference (added by [issue #51](https://github.com/ForkbombEu/credimi-attestbook/issues/51));
- public, unauthenticated retrieval of immutable stored credential schema documents at
  permanent URLs built from the configured public origin (added by
  [issue #98](https://github.com/ForkbombEu/credimi-attestbook/issues/98));
- authenticated, idempotent registration of a local JSON schema document that returns its
  canonical hosted URL, W3C SRI pin, digest and media type, usable as an ordinary
  `schemaReferences[].uri`/`integrity` pair (added by
  [issue #99](https://github.com/ForkbombEu/credimi-attestbook/issues/99));
- anonymous registration and management of pending webhook subscriptions for publicly
  published rulebooks, with a one-time per-subscription management token (added by
  [issue #117](https://github.com/ForkbombEu/credimi-attestbook/issues/117));
- a bounded challenge/response callback verification handshake that activates a subscription
  only after the subscriber's endpoint proves control, with verification-time SSRF checks and
  no redirect following (added by
  [issue #118](https://github.com/ForkbombEu/credimi-attestbook/issues/118));
- signed publication notifications with a durable, restart-safe delivery outbox, bounded
  exponential-backoff retries and a management-token-protected delivery-status view (added by
  [issue #119](https://github.com/ForkbombEu/credimi-attestbook/issues/119) and
  [issue #120](https://github.com/ForkbombEu/credimi-attestbook/issues/120)).
- the public, unauthenticated `GET /openapi.json` machine-readable contract document,
  generated by the same `buildOpenApiDocument()` as the API contract and carrying no
  deployment credential (added by
  [issue #125](https://github.com/ForkbombEu/credimi-attestbook/issues/125));
- the public, unauthenticated interactive reference at `GET /docs`, which renders Scalar
  from UI assets bundled with the application and reads the canonical same-origin
  `/openapi.json` at runtime. It documents the product API only, adds no route schema and
  is not the TS11 catalogue API (added by
  [issue #126](https://github.com/ForkbombEu/credimi-attestbook/issues/126)).

The public API is the integration boundary for Credimi. The standalone adapter documented in
[`docs/credimi-integration.md`](credimi-integration.md) (issue #49) consumes these routes only:
it exposes rulebook selection, version pinning, credential validation, capture-evidence
correlation, headless-wallet comparison and a reproducible conformance run without database
access or a Credimi runtime dependency. It adds no route.

Deliberately **not** in this slice:

- the TS11 catalogue interface (`GET/PUT/DELETE /schemas`, JWS responses) — it must be
  implemented separately and exactly if a later issue adds it (architecture §5);
- capture validation and validation-result persistence; no route pretends to offer them;
- a broker, WebSocket/SSE push or second delivery service. Publication notifications are
  webhook `POST`s driven by an in-process dispatcher over SQLite (§3.15.2 and §3.15.3), not a
  message broker or a live stream;
- provider-management HTTP routes, generic API rate limiting and token expiry/rotation —
  future hardening; the administrator login has its own failure limit, anonymous subscription
  registration has its own per-client quota, and the implemented write-auth model is
  documented in [`docs/security.md`](security.md);
- document replacement or deletion: registration is append-only and content-addressed, so no
  route updates, replaces or deletes a stored schema document;
- a publication signature: no export claims one. OWF 0.5.4 signs only a bare OWF-profile
  `SchemaMeta` compact JWS and does not implement the TS11 v1.0.1 catalogue-response JWS,
  while a version snapshot is not a `SchemaMeta` document; the manifest reports this boundary
  instead of inventing proprietary signing semantics
  ([`docs/standards.md`](standards.md) §5.8 and §6.2). The editor's draft document is a
  working-copy projection, not a version snapshot or a standards document. The catalog,
  rulebook-detail, credential playground and draft-editor views are documented in
  [`docs/ui.md`](ui.md); they are UI routes, not API routes.

Every handler calls the real registry, import or validation service. A service that is not
wired answers `503` with a typed code instead of a placeholder success response.

## 2. Versioning policy

- The product API lives under **`/api/v1`**. The major version is part of the URL; there is
  no separate version header.
- `GET /health` is an unversioned operational endpoint used by container health checks. It
  is not part of the product resource API and does not follow `/api/v1` path changes.
- `GET /openapi.json` is an unversioned documentation endpoint. It serves the generated
  contract document for the versioned product API; the API's major version stays in
  `/api/v1`, and the endpoint is not itself a versioned resource route.
- `GET /docs` is the public, unauthenticated interactive reference for that same generated
  document. It is a UI route served from the built entry document, not a versioned resource
  route, and it adds no route schema of its own: Scalar is bundled with the UI and reads
  `/openapi.json` from the same origin at runtime. It documents the product API only.
- Within `v1` the contract evolves **additively**: new optional response fields, new
  endpoints and new optional request members are allowed. Removing or renaming a field,
  changing a type or status, or making an optional request member required is a breaking
  change and requires `/api/v2`.
- The OpenAPI document's `info.version` tracks the contract document (currently `1.17.0`,
  additive after the lifecycle and comparison operations added by #41, the publication
  export operations added by #42, issuer discovery added by #43, issuer fixture generation
  added by #44, the mock-backed capture explorer added by #48, the optional pinned
  correlation digest added by #49, the read-only headless-wallet comparison added by
  #50, the reproducible conformance run added by #51, the public hosted
  credential-schema document reads added by #98, the authenticated schema document
  registration added by #99, hosted-schema issuer fixture grounding added by #102, the
  hosted/external schema provenance projection added by #103, the public publication
  event feed added by #116, anonymous webhook subscription registration and management
  added by #117, the callback verification and activation handshake added by #118, and the
  durable delivery outbox, retries and delivery-status view added by #120); it is separate
  from the package version reported by `/health`.
- Clients must tolerate unknown response fields. Unknown request members are ignored by the
  handlers except where the API deliberately projects a whitelist (internal registry
  metadata, provenance and the import identity can never be set through the API).

## 3. Resource surface

All paths below are prefixed with the API base. `auth` means an AttestBook provider bearer
token in the `Authorization: Bearer <token>` header; `session` means the opaque administrator
browser-session cookie set by `/api/v1/auth/login`; `subscription` means the per-subscription
management token in the same `Authorization: Bearer <token>` header, which authorizes that
one subscription only. The credential paths are independent. All operations are synchronous
in Phase 1.

Representations are the public projection of the services: rulebook `provenance`,
`metadata` and `importKey`, attestation/schema-reference `metadata` and version `provenance`
are **never** returned by the catalogue and version reads. The publication export manifest is
the one deliberate exception, because FR-008 requires published artifacts to be associated
with provenance metadata; it carries a bounded projection (`adapter`, `sourceUrl`,
`contentDigest`, `retrievedAt`, `profile`, `conformance`, `importedAt`) rather than the raw
version provenance, so import-internal and untrusted source fields never reach the public
manifest. The manifest is a product artifact, not a standards document. The import preview
omits the importer-internal canonical document; that document is derived data used only to
commit an import.

### 3.1 Success envelopes

Single resources and action results use `{ "data": ... }`. The rulebook catalogue also
carries pagination:

```json
{
  "data": [{ "id": "...", "name": "...", "publicationStatus": "published" }],
  "pagination": { "limit": 50, "offset": 0, "total": 1 }
}
```

`limit` and `offset` are applied after the provider/status filters; `total` is the filtered
count. The Phase 1 registry listing is in-memory, which is acceptable for the bounded MVP
catalogue and is the documented limitation until a paginated store query exists.

`GET /api/v1/providers` uses the same `{ "data": [...] }` envelope. Its public projection
contains only `id`, `name` and `createdAt`: publication authority, registry metadata and
tokens are never exposed.

`POST /api/v1/rulebooks` and `POST /api/v1/rulebooks/{rulebookId}/versions` return `201` and
a `Location` header pointing at the canonical GET path. The other writes and imports return
`200` with the resulting representation.

### 3.2 Draft editor documents

The editor works on the normalized working copy through one document, not on a version
snapshot and not on a TS11/OWF wire document:

```json
{
  "id": "...",
  "providerId": "...",
  "name": "PID Rulebook",
  "description": "...",
  "sourceUrl": "https://issuer.example.org/rulebooks/pid",
  "applicableSpec": "ts11@1.0.1",
  "publicationStatus": "draft",
  "attestations": [
    {
      "name": "Person Identification Data",
      "attestationLoS": "iso_18045_high",
      "bindingType": "key",
      "supportedFormats": ["dc+sd-jwt"],
      "schemaReferences": [
        {
          "formatIdentifier": "dc+sd-jwt",
          "uri": "https://issuer.example.org/schemas/pid",
          "integrity": null
        }
      ]
    }
  ],
  "schemaReferences": [],
  "createdAt": "...",
  "updatedAt": "..."
}
```

`PUT /api/v1/rulebooks/{rulebookId}/draft` replaces the whole document in one transaction:
rulebook metadata, attestation types and both per-attestation and rulebook-level schema
references. Internal provenance, metadata, the import identity and publication state are not
accepted from the caller; a whitelist projection strips them first. An attestation matched by
name and a reference matched by attestation, `formatIdentifier` and `uri` keep their
registry-internal metadata and identity, so saving an imported draft unchanged does not
reset its importer provenance; new or changed entries start with `{}`. The write is
**idempotent** (the same document produces the same working copy), authorized by the owning
provider's bearer token, and allowed only while the rulebook's working copy status is
`draft`. Published and historical rulebooks answer `409 immutable`; an invalid document
answers `400` and leaves the previous working copy untouched. Editing a rulebook that has
published versions never mutates those snapshots or their content-addressed artifacts.

`POST /api/v1/rulebooks/validate-draft` takes the same document shape minus the registry
ids and writes nothing. Its report is:

```json
{
  "data": {
    "valid": false,
    "saveable": true,
    "profile": "ts11@1.0.1",
    "diagnostics": [
      {
        "severity": "error",
        "code": "invalid_member_value",
        "message": "format \"mso_mdoc\" is not listed in supportedFormats",
        "path": "attestations.0.schemaReferences.0.formatIdentifier"
      }
    ],
    "limitations": ["Live standards validation covers the TS11 v1.0.1 baseline; ..."]
  }
}
```

`valid` is true only when no structural or standards-level error is present. `saveable`
distinguishes structural failures, which block the `PUT`, from standards findings: the
registry stores profile enumerations as extensible text (decision D-5), so an out-of-baseline
value is reported but does not prevent persisting a work-in-progress draft. `profile` is
`null` when the document's `applicableSpec` is outside the implemented TS11 v1.0.1 live
checks. Standards validation projects each attestation type into a SchemaMeta document (the
source URL stands in for the rulebook URI; a fixed placeholder is used when no source URL is
set) and runs the real adapter, so the editor reports actual adapter findings rather than a
second hand-written rule set. It makes no TS11 or ETSI conformance claim.

### 3.3 Version comparison and publication readiness

`GET /api/v1/rulebooks/{rulebookId}/versions/{version}/compare?to={label}` compares the
authored content of two stored snapshots. The path version is the baseline, `to` is the
compared version, and both must belong to the same rulebook. The comparison is a structural
diff, not a byte diff: the snapshot identity fields (`format`, `rulebookId` and the version
label) are excluded, so two labels with the same content report `identical: true`. Object
keys are visited in sorted order and the change list is sorted by JSON Pointer path, so the
same two snapshots always produce the same response. Each change is `added`, `removed` or
`changed` and carries the `before` and/or `after` value.

`GET /api/v1/rulebooks/{rulebookId}/versions/{version}/publication-readiness` is a public,
read-only assessment. It executes the checks this build can actually run and reports them
individually:

| Check | Meaning |
| --- | --- |
| `draft_version` | Only a `draft` version can be published; published and historical artifacts are immutable. |
| `rulebook_status` | The rulebook working copy may move to `published`. A leftover draft on an already-published rulebook is not publishable until the next draft version reopens the working copy; a historical rulebook never is. |
| `snapshot_integrity` | The stored bytes still hash to the recorded SHA-256 digest. |
| `snapshot_current` | The draft snapshot still matches the current working copy; a stale draft must be refreshed. |
| `content_valid` | The snapshot content passes the same structural and TS11 v1.0.1 standards validation the editor runs. |
| `standards_profile` | Whether the profile baseline was actually validated; an unsupported profile is a warning, not a silent pass. |
| `attestation_types` | The rulebook defines at least one attestation type. |

`ready` is true only when no check reports `fail`. The response also carries explicit
`limitations`: remote schema documents, issuer trust, signing and interoperability are not
verified by these checks, and the assessment makes no TS11 or ETSI conformance claim.
Readiness is advisory for direct API callers; `POST .../publish` remains the authoritative
transition and still rejects a stale snapshot with `409 conflict`.

The rulebook-status check mirrors the publish transition exactly: a draft version cannot be
published while its rulebook is `published` (it answers `409 immutable`) or `historical`.
Creating the next version returns a `published` rulebook to `draft`, after which a leftover
draft version can be published and supersedes the current published version.

### 3.4 Publication export and integrity

`GET /api/v1/rulebooks/{rulebookId}/versions/{version}/export` is the publication-grade
retrieval route. It returns the exact stored bytes of a **published or historical** version,
never a re-serialization: the bytes must still hash to the recorded digest or the request
fails as a server fault. `Content-Digest` carries the RFC 9530 structured SHA-256 value,
`ETag` carries the quoted hex digest, and `Content-Disposition` names the download from the
frozen rulebook name and version label. A draft version is a working copy, not a publication
artifact, and answers `409 conflict`. The existing `/content` route remains the unbounded
exact-bytes read for any version, including drafts.

`GET /api/v1/rulebooks/{rulebookId}/versions/{version}/export/manifest` describes the same
artifact without copying it:

```json
{
  "data": {
    "format": "attestbook.publication-export@1",
    "rulebookId": "...",
    "providerId": "...",
    "version": "1.0",
    "status": "published",
    "name": "PID Rulebook",
    "sourceUrl": "https://issuer.example.org/rulebooks/pid",
    "specVersion": "ts11@1.0.1",
    "mediaType": "application/vnd.attestbook.rulebook-version+json",
    "contentDigest": "…64 lowercase hex characters…",
    "byteLength": 1234,
    "createdAt": "…",
    "publishedAt": "…",
    "provenance": {},
    "integrity": { "algorithm": "sha256", "verified": true },
    "signature": {
      "status": "unsupported",
      "reason": "OWF 0.5.4 signs only a bare OWF-profile SchemaMeta compact JWS. …"
    },
    "limitations": ["…"]
  }
}
```

Every manifest field comes from frozen data: the version row, a bounded projection of its
provenance and the snapshot document. The rulebook's mutable working copy is never read, so the
manifest for a published version is identical across repeated exports and is unaffected by later
edits, a new draft version or supersession. `status` changes from `published` to `historical`
when a newer version supersedes it; the digest, publication time, bytes and bounded provenance
do not change.

The manifest makes **no signature claim**. The mandatory OWF package provides only a bare
OWF-profile `SchemaMeta` compact JWS (`signSchemaMeta`/`verifySchemaMeta`), which the
standards adapter already uses for that supported operation
([`docs/standards-adapter.md`](standards-adapter.md) §6). A version snapshot is not a
`SchemaMeta` document and OWF 0.5.4 does not implement the TS11 v1.0.1 catalogue-response
JWS, so the export reports `signature.status: "unsupported"` instead of inventing a
proprietary signature. Integrity is the SHA-256 digest, which consumers must recompute over
the exported bytes.

Publication itself stays an authenticated, owner-scoped transition
(`POST .../publish`); the export reads are public, matching the public catalogue reads. Each
publication writes the `version.publish` audit row with the actor provider, version,
digest, profile and superseded versions, in the same transaction as the state change.

### 3.4.1 Publication event feed

`GET /api/v1/rulebooks/{rulebookId}/events` is the public, unauthenticated discovery route
for publication: it names the exact immutable version that was published, without returning
the rulebook working copy and without requiring a client to read every rulebook.

Each successful **new** publication appends exactly one durable `rulebook.published` event
inside the publication transaction. Draft creation, draft refresh, a failed or stale
publication and the idempotent replay of an already-published version append nothing. The
event carries its own product shape version (`format`, stored with the row), is not a
TS11/ETSI wire document, and is documented by this versioned API contract:

```json
{
  "data": [
    {
      "id": "…stable event id…",
      "format": "attestbook.rulebook-publication-event@1",
      "type": "rulebook.published",
      "rulebookId": "…",
      "version": "1.0",
      "contentDigest": "…64 lowercase hex characters…",
      "publishedAt": "2026-01-01T00:00:00.000Z"
    }
  ],
  "pagination": {
    "limit": 50,
    "nextCursor": "opaque-cursor-or-null",
    "hasMore": false
  }
}
```

Events are returned in ascending publication order. `limit` defaults to 50 and is bounded at
100; pagination is cursor based, not offset based. Pass the opaque `pagination.nextCursor`
value as `cursor` to read the next page; `nextCursor` is `null` on the last page. A cursor
names a feed position, so a publication appended between two requests appears after the
issued cursor and never shifts, duplicates or skips earlier events. The opaque cursor is
stable across process restarts and is not a credential. The `rulebookId`, `version` and
`contentDigest` values pin the immutable snapshot: `GET .../versions/{version}/content` or
`.../versions/{version}/export` retrieves the exact bytes. Supersession changes the version's
status to `historical` but keeps its event, and a new draft never removes history. An
unknown rulebook answers `404 not_found`; an invalid `limit` or `cursor` answers
`400 invalid_request`.

The event deliberately carries only public publication provenance. Provider identity,
publication authority, provider tokens, working-copy content, credentials, version
provenance and audit metadata are never included. The feature does not backfill events for
versions published before it existed; only publications performed by a build that includes
it append events.

### 3.5 Issuer metadata discovery

`POST /api/v1/issuers/discover` is the authenticated, read-only FR-006 slice. The request is
the Credential Issuer Identifier:

```json
{ "credentialIssuer": "https://issuer.example" }
```

Discovery inserts `/.well-known/openid-credential-issuer` into the issuer identifier between
the host and the path (OpenID4VCI 1.0 §12.2.2), then retrieves it under the import pipeline's
§15 controls (https-only URL validation, public-address pinning, redirect re-validation, total
deadline, response-size and JSON-shape bounds), validates the members it uses and extracts the
supported credential configurations. An explicit earlier appended-path metadata URL is also
accepted for older issuers. It understands the OpenID4VCI 1.0 `credential_configurations_supported`
object and the earlier `credentials_supported` shape.

Each configuration reports its `format`, type identifiers (`vct`/`doctype`/legacy `type`;
`vct` is a case-sensitive StringOrURI and may be a URN), display name, exposed schema references
and a `mapping` with `status`, `candidates` and, for an unmatched configuration, a `reason`.
`matched` carries exactly one candidate, `ambiguous` more than one and `unmatched` none. Every
candidate is an **exact pin**:

```json
{
  "rulebookId": "…",
  "rulebookName": "PID Rulebook",
  "version": "1.0",
  "contentDigest": "…64 lowercase hex characters…",
  "specVersion": "ts11@1.0.1"
}
```

Only published or historical rulebook versions are candidates; drafts are mutable and never
used. Several matching versions of the same rulebook collapse to its current version, so a
single history does not look ambiguous; matching several rulebooks is reported as ambiguous
rather than resolved by a policy the API has not been given. The result also carries the
retrieval provenance (`metadataUrl`, redirects, retrieval time, content type, byte length and
the SHA-256 of the exact bytes), bounded issuer fields, aggregate counts, diagnostics and
limitations.

The route writes nothing: discovered issuers, metadata snapshots and explicit manual mappings
are not persisted in this slice. Issuer metadata is never treated as rulebook content, no
exposed reference is fetched and no signature, trust or conformance result is derived from it.
The discovery contract is documented in [`docs/discovery.md`](discovery.md).

### 3.6 Issuer fixtures

`POST /api/v1/issuers/fixtures` is the public FR-013 slice. It synthesizes an **unsigned**
credential claim payload from the JSON Schema 2020-12 attribute constraints that one pinned
rulebook version references. It is not a credential issuer: the payload carries
`kind: "attestbook.unsigned-issuer-fixture@1"`, `signed: false` and `issued: false`.

```json
{
  "rulebookId": "…",
  "rulebookVersion": "1.0",
  "attestationType": "PID",
  "format": "dc+sd-jwt",
  "schemaDocuments": [
    { "uri": "https://issuer.example/schema/pid.json", "content": "{ … }" }
  ],
  "overrides": [{ "path": "/given_name", "value": "Ada" }]
}
```

The caller supplies the exact schema document bytes for an **external** reference, exactly as
for credential validation. A **canonical AttestBook-hosted** reference — this deployment's
`${PUBLIC_BASE_URL}/api/v1/schema-documents/{documentId}/content` URL — is instead resolved
from the immutable local store, never over HTTP, and needs no `schemaDocuments` entry. Each
URI must be a schema reference of the selected attestation type in that version (and of the
requested `format`, when present), and its sha256 SRI value must match the resolved bytes
before the document can ground a payload. A missing, corrupt, unpinned or mismatched hosted
reference aborts the request with an explicit diagnostic; references without a supplied
external document and SD-JWT VC Type Metadata references are reported and never used; when no
reference is usable the route answers `400 invalid_request` rather than an ungrounded fixture.

The response carries the pinned rulebook evidence, the effective attribute definitions (JSON
Pointer, required flag, types and supported constraints), the generated payload, an explicit
payload-validation status against the applied documents, the applied overrides, labelled
negative cases and limitations. Each `schemaReferences` entry includes `source` (`hosted`,
`caller` or `null`). `overrides` replace existing attributes by JSON Pointer and are
re-validated; an override that deliberately violates a constraint yields
`payloadValidation.status: "FAIL"` with findings instead of pretending success. Negative cases
are derived from the supported constraints in deterministic order, each verified to fail the
applied documents before it is returned. Their `id` is stable (`<category>:<path>`) and
`expected` is always `FAIL`.

Compilation, synthesis, payload evaluation and negative-case verification run in the same
resource-bounded sandbox as credential validation, with a shared concurrency limit. The route
writes nothing and performs no network request. A timeout, memory or output limit answers
`400 invalid_request`; a busy or unavailable sandbox answers `503 fixture_unavailable`. The
contract, supported synthesis subset and non-claims are documented in
[`docs/fixtures.md`](fixtures.md).

### 3.7 Verifier constraints and OpenID4VP-aware mappings

`POST /api/v1/verifiers/constraints` is the public FR-014 slice. It returns the **typed
attribute and format constraints** of one pinned rulebook version and the verifier-policy
interfaces AttestBook can map them to. It is not an OpenID4VP endpoint: the DCQL mapping is an
explicitly partial query fragment and the result carries no proof or protocol result.

```json
{
  "rulebookId": "…",
  "rulebookVersion": "1.0",
  "attestationType": "PID",
  "format": "dc+sd-jwt",
  "schemaDocuments": [
    { "uri": "https://issuer.example/schema/pid.json", "content": "{ … }" }
  ]
}
```

`format` and `schemaDocuments` are optional. Without `format`, every supported format of the
attestation type is resolved. The caller supplies the exact schema document bytes, as for
credential validation and fixtures; each URI must be a schema reference of the selected
attestation type (and of the requested `format`, when present), and its sha256 SRI value must
match before the document can ground constraints. An unpinned reference, an unsupplied
document and SD-JWT VC Type Metadata are reported and never used; a supplied document that
does not match its pin, a foreign URI or an unbounded document is `400 invalid_request`.

Each format reports a `grounding` state, its schema references, the typed attributes (JSON
Pointer, required flag, JSON types, extracted constraints, unresolved keywords and a DCQL claim
path) and a `dcql` mapping. The DCQL mapping has `complete: false`; its `credentialQuery`
contains only the format and claim paths of a `dc+sd-jwt`/`mso_mdoc` rulebook, and every
unexpressible constraint is listed in `unsupported` with a stable `code`, `scope` and reason.
The pinned snapshot has no `vct`/`doctype`, no trusted authorities and no protocol material, so
those gaps are reported instead of fabricated. `policyInterfaces` enumerates the supported
native constraints, the partial DCQL interface and the unsupported Presentation Exchange
interface. `nonClaims` states `presentationRequest: false`, `proof: false` and the
cryptographic/trust/protocol/interoperability dimensions as `NOT_TESTED`.

The route writes nothing and performs no network request. The contract, supported extraction
subset and non-claims are documented in [`docs/verifier.md`](verifier.md).

### 3.8 Capture explorer and pinned-rulebook correlation

`GET /api/v1/captures` is the read model behind UI-006 and FR-019. It is **mock-backed**: the
server seeds it from the deterministic local `MockCaptureSource`s, every entry carries
`source.transport: "mock"`, and no live `capture-issuer`/`capture-verifier` endpoint is
contacted. Pagination is `limit` (default 50, maximum 100) and `offset`.

A list entry is the normalized metadata envelope joined with the exact rulebook version of a
recorded validation and with explicit gaps:

```json
{
  "captureId": "e2e-issued-credential-capture",
  "correlationId": "credimi-e2e-correlation-48",
  "source": { "sourceId": "mock-capture-issuer", "component": "capture-issuer", "transport": "mock", "description": "…" },
  "provenance": { "capturedAt": "2026-11-05T09:48:23Z", "receivedAt": "…" },
  "interactionType": "issuance",
  "protocol": "openid4vci",
  "credentialFormat": "dc+sd-jwt",
  "artifactType": "issued-credential",
  "testExecutionRef": "credimi-e2e-execution-48",
  "declaredRedaction": { "status": "none", "policyRef": null, "redactedPaths": [], "redactedDigest": null },
  "artifact": { "availability": "inline", "mediaType": "application/vc+sd-jwt", "byteLength": 2048, "uri": null },
  "rulebook": null,
  "validation": null,
  "evidenceGaps": [
    { "code": "no_rulebook_binding", "message": "…" },
    { "code": "validation_not_run", "message": "…" }
  ],
  "evidenceComplete": false
}
```

`GET /api/v1/captures/{captureId}` adds the redacted projection (`artifactProjection`), the
source metadata, the ordered `timeline` and the explicit `limitations`. The raw inline
artifact is **never** returned: `artifactProjection.document` is the default-policy redaction
of the JSON artifact (path-preserving `[redacted]` placeholders), and an external reference is
reported with `availability: "external"` and no projection. The stable gap codes are
`external_artifact_not_fetched`, `artifact_redacted_by_source`,
`no_test_execution_reference`, `no_rulebook_binding`, `validation_not_run` and
`validation_not_applicable`; an absent field is never a pass.

`POST /api/v1/captures/{captureId}/validate` takes the pinned selection and an optional
snapshot digest:

```json
{
  "rulebookId": "…",
  "rulebookVersion": "1.0",
  "attestationType": "…",
  "rulebookDigest": "<optional lowercase hex SHA-256>"
}
```

It runs the **real** structural credential engine on the capture's segregated inline artifact
and records the correlation. A supplied `rulebookDigest` that no longer matches the version
snapshot is refused with `409 conflict` before anything is recorded, so a stale pin cannot
overwrite an existing correlation. The response is the engine's `CredentialValidationResult` plus
the exact binding (`rulebook.id`, `name`, `version`, `contentDigest`, `digestVerified`,
`specVersion`, `status`), the attestation type and the AttestBook `boundAt`, together with the
caller-owned `captureId`, `correlationId` and `testExecutionRef` preserved verbatim (FR-019;
AttestBook still does not mint a correlation id, CD-5). The operation writes no registry data,
does not change a pinned snapshot and is not a durable run history. It requires a provider
bearer token because it records server state that every reader sees; the correlation binding
does not carry the acting provider id.

Evidence that cannot be validated honestly is refused with `409 conflict` and a safe message:
an external reference (not fetched) and a non-`issued-credential` artifact type. The
source-redacted refusal remains a defensive check that the version 1 normalizer currently makes
unreachable, because it rejects an inline artifact that already declares redaction and an
external artifact is refused before that check. A malformed request body or query is
`400 invalid_request`; an unknown capture or unknown rulebook/version/attestation type is
`404 not_found`; a capture-source transport failure is `502 capture_fetch_failed`. A
structural validation status never implies cryptographic, issuer-trust, protocol or
interoperability success. The contract and non-claims are documented in
[`docs/capture.md`](capture.md) §9.

### 3.9 Headless-wallet comparison evidence

`POST /api/v1/captures/{captureId}/compare` is the read-only FR-021 seam. It requires the
capture to be correlated already, and it takes an optional caller-supplied external wallet
observation:

```json
{
  "externalWallet": {
    "walletId": "wallet-a",
    "observedAt": "2026-11-05T09:48:30Z",
    "interaction": "issuance",
    "observations": [
      { "dimension": "cryptographic_verification", "status": "PASS", "code": "signature-valid" },
      { "dimension": "issuer_trust", "status": "NOT_TESTED" },
      { "dimension": "protocol_conformance", "status": "PASS", "code": "issuance-flow-complete" },
      { "dimension": "interoperability", "status": "FAIL", "code": "claim-not-presented", "detail": "The external wallet did not present the family_name claim." }
    ]
  }
}
```

It returns the `attestbook.headless-wallet-comparison@1` report. The AttestBook side is the
exact pinned binding (`rulebookId`, `version`, `contentDigest`, `digestVerified`,
`specVersion`, `rulebookStatus`, `attestationType`, `boundAt`), the non-sensitive credential
facts, the schema references and the structural findings. The comparison separates:

- `schema`: the four AttestBook-executable dimensions (`credential_parsing`,
  `format_recognition`, `schema_validation`, `attestation_constraints`);
- `protocol`: `protocol_conformance`, from the external observation only;
- `interoperability`: `interoperability`, from the external observation only;
- `trust`: `cryptographic_verification` and `issuer_trust`, from the external observation
  only;
- `unsupported`: every dimension the comparison cannot establish, with `code`,
  `attestbookStatus` and a reason. The four AttestBook-unexecuted dimensions are always
  listed with `attestbook_does_not_execute`; a structural dimension with no evidence is
  `no_evidence_supplied` and one with non-conclusive values is `not_comparable`.

Each dimension entry reports `attestbook`, `external` and a `result` of `agreement`,
`divergence`, `attestbook_only`, `external_only`, `not_provided` or `not_comparable`. The
external observation is recorded as bounded input, labelled `external`, and never changes an
AttestBook validation status; `nonClaims` fixes `externalObservationVerified` and the four
unexecuted dimensions to `false`. The operation is public and read-only: it persists nothing,
starts no wallet and contacts no Credimi or capture endpoint. `404` means an unknown capture,
`409` an uncorrelated capture, `400` a malformed observation, `503` an unwired capture
explorer and `502` a failing capture source. The contract, bounds and non-claims are documented
in [`docs/headless-wallet-comparison.md`](headless-wallet-comparison.md).

`attestbook.conformance-result@1`, a machine-readable result for recurring validation:

### 3.11 Administrator browser session

The optional single-administrator login (issue #88) is configured entirely from the server
environment: `ADMIN_USERNAME`, `ADMIN_PASSWORD_HASH` (an Argon2id PHC hash with at least
19 MiB of memory and two passes) and `ADMIN_PROVIDER_ID` (an existing provider). The group is
all-or-nothing; a missing, partial or invalid group makes login answer `503 auth_unavailable`
without affecting the public API or provider bearer writes. The full model is in
[`docs/security.md`](security.md) §2.1.

`POST /api/v1/auth/login` takes `{ "username": "...", "password": "..." }` and requires
`Content-Type: application/json`. Success is `200`:

```json
{
  "data": {
    "provider": { "id": "…", "name": "…", "createdAt": "…" },
    "expiresAt": "2026-01-01T08:00:00.000Z",
    "csrfToken": "…"
  }
}
```

and the response sets `attestbook_admin_session` with `HttpOnly`, `SameSite=Lax`, `Path=/`,
an eight-hour absolute `Max-Age`, and `Secure` when the request is HTTPS (directly or through
`X-Forwarded-Proto: https`). The identifier is a 256-bit opaque value, stored only as a
SHA-256 hash; no bearer token, password or session identifier appears in the body. An unknown
username and a wrong password get the same `401` with `unauthorized` and no
`WWW-Authenticate` challenge. Login and logout reject a foreign `Origin`/`Sec-Fetch-Site` with
`403`. Repeated failures answer `429 rate_limited` with `Retry-After` (five per account and
twenty per client address in fifteen minutes). An attempt reserves its failure slot before the
password check, and at most four checks run concurrently, so parallel requests cannot exceed
the bound; a successful login clears the counters and rotates away any session the browser
presented.

`csrfToken` is the session-bound CSRF value (issue #89). Every state-changing request that
authenticates with the session cookie instead of a bearer token must send it in the
`X-CSRF-Token` header; a missing or wrong value answers `403 csrf_failed` and changes nothing.
The token is minted with the session, rotated by the next login and returned again by
`GET /api/v1/auth/me`, so a reloaded page can continue writing. It is never set as a cookie.

`GET /api/v1/auth/me` resolves the cookie to the bound provider and returns the same `data`
shape, including the live `csrfToken`; `401` means no live session.
`POST /api/v1/auth/logout` revokes the session row and expires the cookie, answers `204`, and
is idempotent; when a live session cookie is present it also requires `X-CSRF-Token`, while a
request with nothing to revoke still answers `204`. None of these routes accept a session
identifier from a URL, and nothing is stored in browser storage.

### 3.12 Dual-transport authorization of the write routes

The protected write routes listed in [`docs/security.md`](security.md) §3.1 accept either the
`Authorization: Bearer <token>` header or the `attestbook_admin_session` cookie (issue #89).
Both resolve to the same provider actor, so ownership rules, `401`/`403` semantics, provider
attribution and audit rows do not depend on the credential used.

- A present `Authorization` header is authoritative. A malformed, unknown or revoked bearer
  answers `401` and never falls back to a cookie session; a valid bearer ignores any cookie.
- A cookie request must send `X-CSRF-Token` when the operation is not a `GET`. The header is
  documented as an optional parameter on every protected non-GET operation, because the bearer
  path does not need it.
- With neither credential the route answers `401`; a cookie without CSRF evidence answers
  `403 csrf_failed`. Anonymous catalogue, validation and download reads are unchanged.

### 3.13 Provider-authorized schema registration

`POST /api/v1/schema-documents?kind={kind}` registers one local schema document under the
authenticated provider (issue #99). It accepts the provider bearer token or the administrator
browser session with its session-bound `X-CSRF-Token`; anonymous registration is refused with
`401`, and an explicit invalid bearer never falls back to a cookie.

The request body is the exact JSON document, not an envelope:

- `kind=json_schema_2020_12` stores the bytes as `application/schema+json`; the document must
  be a JSON Schema 2020-12 object or boolean that the validation engine can compile safely.
  The same unsafe constructs refused by validation are refused here (`$ref`/`$dynamicRef`,
  `pattern`, `format`, `uniqueItems`, unknown keywords and non-2020-12 dialects).
- `kind=sd_jwt_vc_type_metadata` stores the bytes as `application/json`; the document must
  satisfy the pinned `@sd-jwt/sd-jwt-vc` type metadata format with a non-empty `vct`.
- The bytes must be strict UTF-8, must not repeat a member name, are bounded to 256 KiB, a
  nesting depth of 64 and 32 768 parsed values, and are bounded again by the shared 4 MiB
  request limit. A body over 256 KiB answers `413 payload_too_large`; malformed JSON,
  unsupported profiles or unsafe constructs answer `400 invalid_request`.
- The `kind` query parameter, not the `Content-Type` header, selects the profile. A JSON
  Schema request may therefore use `application/schema+json` or `application/json`.

The response is the same public projection as the read routes, so `url`, `integrity`,
`contentDigest` and `mediaType` describe the exact stored bytes:

```json
{
  "data": {
    "id": "6f0e2c1a-...",
    "kind": "json_schema_2020_12",
    "mediaType": "application/schema+json",
    "contentDigest": "<lowercase hex sha-256>",
    "integrity": "sha256-<base64>",
    "url": "https://schemas.example/api/v1/schema-documents/6f0e2c1a-.../content",
    "createdAt": "2026-01-01T00:00:00.000Z"
  }
}
```

- A new association answers `201` and a `Location` header carrying the hosted URL; replaying
  the same content for the same provider answers `200` with the original document unchanged.
  Identical content registered by a different provider gets its own id and URL while the bytes
  are stored once.
- Registering the same bytes under a contradictory profile answers `409 conflict`. The
  per-provider association limit is 100; a provider at the limit gets `409 conflict` for a new
  document but can still replay the documents it already owns.
- `503 public_base_url_unavailable` is answered before any write when the deployment has no
  valid `PUBLIC_BASE_URL`, because the canonical URL is part of the result. There is no route
  that replaces, updates or deletes a stored document; the bytes and their digest are
  immutable.

The returned `url` and `integrity` are ordinary schema-reference values. An authorized caller
writes them into an existing per-attestation `schemaReferences` entry through
`POST /api/v1/rulebooks` or `PUT /api/v1/rulebooks/{rulebookId}/draft`:

```json
{
  "formatIdentifier": "dc+sd-jwt",
  "uri": "https://schemas.example/api/v1/schema-documents/<id>/content",
  "integrity": "sha256-<base64>"
}
```

Neither the draft API nor the version snapshot learns that the URI is AttestBook-hosted: the
snapshot serializes the same `formatIdentifier`, `uri` and `integrity` members, with no
proprietary field. An external absolute `https` schema URI and optional SRI keep working
exactly as before, without an upload or conversion, and an omitted SRI stays `null`.

### 3.14 Hosted-schema provenance in detail, draft and version reads

The public read projections derived from the registry (`GET .../schema-references`,
`GET .../attestations`, `GET .../draft` and `GET .../versions/{version}/schema-references`)
add a `hostedSchema` member to every reference (issue #103):

```json
{
  "formatIdentifier": "dc+sd-jwt",
  "uri": "https://schemas.example/api/v1/schema-documents/<id>/content",
  "integrity": "sha256-<base64>",
  "hostedSchema": {
    "id": "<id>",
    "kind": "json_schema_2020_12",
    "mediaType": "application/schema+json",
    "contentDigest": "<lowercase hex sha-256>",
    "integrity": "sha256-<base64>",
    "url": "https://schemas.example/api/v1/schema-documents/<id>/content",
    "createdAt": "2026-01-01T00:00:00.000Z"
  }
}
```

- `hostedSchema` is `null` for an external reference. The member is a read-only,
  store-derived projection: it is not persisted, does not enter the Draft JSON or a version
  snapshot, and does not change the TS11 `SchemaMeta` boundary (TS11 carries schema URIs,
  not embedded bodies).
- The association is exact, not a URL-prefix guess: the reference URI must equal the
  canonical content URL of a stored document built from the configured `PUBLIC_BASE_URL`.
  A look-alike host, an extra path segment, a query, a fragment or a near-miss path stays an
  external reference.
- The projection carries only the public document fields the content route already exposes.
  Provider ownership, registration provenance, bearer tokens and private records are never
  returned.
- `GET .../versions/{version}/schema-references` reads the exact frozen snapshot for that
  version and groups its references by attestation type, plus rulebook-level references. It
  reports the version label, content digest, status and publication time so a consumer can
  name the exact version a hosted document is referenced by. The snapshot bytes themselves
  are never rewritten and remain the export artifact.
- The UI compares the persisted `integrity` pin with the stored document's `sha256-<base64>`
  value and reports a missing or mismatching pin rather than presenting it as verified.
  See [`docs/schema-authoring.md`](schema-authoring.md) for the complete local authoring,
  publication and consumption walkthrough.

### 3.15 Anonymous webhook subscriptions

`POST /api/v1/rulebooks/{rulebookId}/subscriptions` registers a consumer that wants to follow
a rulebook's publications without an AttestBook account, provider bearer token, browser
session or CSRF token. Publishing and editing rulebooks remain authenticated exactly as before.
Registration only stores a `pending` subscription and **never contacts the callback host**;
an explicit verification request (§3.15.1) activates it, and publishing a new version then
durably enqueues one signed `rulebook.published` notification per active, verified subscriber
(§3.15.2). An in-process dispatcher leases and retries those jobs, and the subscriber can read
their bounded delivery status (§3.15.3).

Request body (unknown members are ignored):

```json
{ "callbackUrl": "https://subscriber.example.test/webhook" }
```

The request must use `Content-Type: application/json`; a different content type or none
answers `400 invalid_request`. This forces a CORS preflight for a cross-site form or no-cors
fetch, so a third-party page cannot make a visitor's browser register a subscription (the
application sends no CORS headers).

`callbackUrl` is required, bounded to 2,048 characters before and after normalization, and
must be an absolute `https` URL without embedded credentials or a fragment. The raw text must
be printable ASCII without backslashes, so a parser-difference form cannot hide another host.
The host must be a public DNS name with valid labels and at least two labels, or a public IP
literal; single-label names, `localhost`, `.localhost`, `.local`, `.internal`, `.home.arpa`,
trailing-dot hosts and blocked IP ranges (loopback, private, link-local, carrier-grade NAT,
multicast, reserved and cloud-metadata) are rejected. Registration performs no DNS lookup and
no outbound request. Verification re-validates and resolves the stored URL and connects to the
pinned address, so a name that later resolves to an internal address cannot redirect the
verification request. A plain `http` URL on a literal loopback address is accepted only by a
service-level test opt-in; production wiring keeps it off, and the local UAT start script
enables it for a disposable callback server. A DNS name is never allowed to resolve to
loopback, even with the opt-in.

The rulebook must already exist and have at least one published or historical version. Its
working copy may be a draft for the next version, because the rulebook is still publicly
readable and has published artifacts. An unknown rulebook answers `404`; a rulebook with no
published version, or one already at its live-subscription bound, answers `409`; an invalid or
unsafe URL answers `400`; and an oversized body answers `413`. None of these creates a record.
Registrations are additionally bounded per client in an in-process sliding window (ten
successful registrations per ten minutes by default); exceeding it answers `429` with
`Retry-After` and `details.retryAfterSeconds`. The client key is the socket's remote address:
`X-Forwarded-For` and other request forwarding headers are never trusted, so behind a reverse
proxy all clients share the proxy's address. IPv4 is keyed per address; IPv6 is keyed per /64,
because one host normally controls a whole /64, and an IPv4-mapped IPv6 address is keyed as the
IPv4 client it represents. The limiter tracks at most 10,000 keys and drops the oldest
insertion-order key beyond that, so a client able to present very many keys could displace its
own entry. The quota is not persisted and resets on restart. The per-rulebook bound (1,000 live
subscriptions by default) is durable and enforced against SQLite. No client address is stored.
Subscriptions themselves do not expire and there is no operator cleanup, so a rulebook whose
bound is full stays closed to new registrations until subscribers revoke rows; only the
verification challenge and the verification-attempt window are time-bounded.

Success is `201` with a `Location` header and one `RegisteredSubscription`:

```json
{
  "data": {
    "id": "<opaque subscription id>",
    "rulebookId": "<rulebook id>",
    "callbackUrl": "https://subscriber.example.test/webhook",
    "state": "pending",
    "createdAt": "2026-01-01T00:00:00.000Z",
    "updatedAt": "2026-01-01T00:00:00.000Z",
    "managementToken": "ats_<opaque token>",
    "webhookSecret": "atw_<derived secret>"
  }
}
```

The `managementToken` is 256 random bits and is returned **exactly once**. The database stores
only its SHA-256 hash, so the API can never return it again and a database leak does not yield
a usable management credential. The registered state is `pending` and therefore not delivery
eligible; `POST /api/v1/subscriptions/{subscriptionId}/verify` proves control of the callback
and activates it.

`webhookSecret` is present only when the deployment configured
`SUBSCRIPTION_WEBHOOK_SIGNING_KEY`. It is derived with HMAC-SHA-256 from that deployment key and
the subscription id, so it is stable across restarts and independent per subscription, and it is
never stored in the database. It is returned once here, exactly like the management token, and
never appears in a readable subscription projection, an error or a log. The subscription row
stores only a truncated, non-secret fingerprint of the deployment key it was registered under,
so delivery can tell whether the subscriber was ever given the current secret. A deployment
without the key performs no publication delivery and issues no secret instead of falling back to
a generated or committed key; the server logs a warning at startup. A subscription registered
without a key, or under a key that has since changed, is never contacted and cannot be made
verifiable retroactively; the subscriber re-registers under the current key.

`GET /api/v1/subscriptions/{subscriptionId}` and
`DELETE /api/v1/subscriptions/{subscriptionId}` require the per-subscription management token
as `Authorization: Bearer <managementToken>`. A provider bearer token, the administrator
session cookie and every other credential have no authority on these routes:

- `GET` returns the same public fields without `managementToken` or `webhookSecret` (and without
  the stored token hash).
  It is the only way to read the subscriber's own normalized callback URL. Any missing,
  malformed, invalid or foreign token and any unknown subscription id answer the same `401`
  `unauthorized`, so the response does not disclose whether another subscriber's id exists. A
  revoked subscription answers `404`.
- `DELETE` revokes the subscription immediately, ending its future delivery eligibility, and
  answers `204` with no body. The row and its token binding are retained, so repeating the
  delete with the same valid token answers `204` again (idempotent). An unknown id or an
  invalid token still answers `401`, and no other credential can revoke the record.

Neither route returns a token, a token hash, a webhook secret, a client address or provider
ownership data. Both set `Cache-Control: no-store`, as does the registration response because it
carries one-time secrets. Raw management tokens and webhook secrets are never logged or written
to an error message. See [`docs/security.md`](security.md) §2.2, §2.4, §6 and §8 for the
credential and residual-risk model.

### 3.15.1 Callback verification and activation

`POST /api/v1/subscriptions/{subscriptionId}/verify` is the explicit activation handshake. It
accepts the same `Authorization: Bearer <managementToken>` credential as the management
routes, no request body, and never reads a provider credential or the session cookie. A
pending subscription triggers exactly one outbound request; an invalid or foreign token, an
unknown id and a missing credential answer the same `401` as the management routes, and a
revoked subscription answers `404`. An already-active subscription is returned with `200` and
is **not** contacted again.

The handshake is one HTTP request to the stored callback URL:

```http
POST /webhook HTTP/1.1
Host: subscriber.example.test
Content-Type: application/json
Accept: application/json

{
  "type": "attestbook.subscription.verification@1",
  "challenge": "atv_<fresh 256-bit challenge>",
  "expiresAt": "2026-01-01T00:05:00.000Z"
}
```

The endpoint proves control by answering `200` with a JSON object carrying the exact
challenge:

```http
HTTP/1.1 200 OK
Content-Type: application/json

{ "challenge": "atv_<the same challenge>" }
```

The challenge is fresh for every initiation, expires after five minutes and is stored only as
its SHA-256 hash, so it is not readable from the database or from any later API response. A
failed attempt consumes the challenge: a retry requires a new initiation and is charged to the
attempt bound. Redirects are **not** followed (`3xx` fails), so every request goes to exactly
the address that was checked. The response body is capped at 8 KiB and only a `200` answer with
`application/json` (or a `+json` media type) and an object `challenge` member is accepted.

Network safety is enforced at verification time, not trusted from registration:

- The stored URL is re-validated under the registration policy, then its hostname is resolved
  once. Every resolved answer must be public; a mixed public/private answer is refused.
- The transport connects to the validated address and presents the original hostname only for
  HTTPS SNI and `Host`, so a second DNS answer cannot redirect the connection.
- Loopback, private, link-local, carrier-grade NAT, multicast, reserved and cloud-metadata
  addresses are refused in IPv4, IPv6 and IPv4-mapped/NAT64 forms. A literal
  `127.0.0.1`/`::1` `http` target is permitted only by the explicitly configured test-loopback
  opt-in; a DNS name resolving to loopback is still refused.
- The DNS lookup, connection and request share a five-second bound, and the response is read
  under the byte cap.

Failures keep the subscription `pending` and carry a stable reason:

| Condition | HTTP | `error.code` | `details.reason` |
| --- | --- | --- | --- |
| Wrong challenge, wrong or malformed body, wrong content type, expiry, non-`200` status, redirect, oversized body | `409` | `verification_failed` | `challenge_mismatch`, `invalid_response`, `expired_challenge`, `unexpected_status`, `redirect_not_followed`, `response_too_large` |
| A re-validated destination is not public, or the stored URL no longer passes the policy | `409` | `verification_failed` | `blocked_target` |
| DNS failure, connection/TLS failure or timeout | `502` | `callback_unreachable` | `dns_failure`, `network_failure`, `timeout` |
| A different handshake is already in progress | `409` | `conflict` | — |
| More than five initiations in ten minutes for one subscription | `429` | `rate_limited` | `Retry-After` + `details.retryAfterSeconds` |

No error message contains the challenge, the management token or its hash. Activation is
final apart from revocation: the database requires `verified_at` for an `active` row and
forbids it on a `pending` one, and an activated row can only become `revoked`. Activation
makes the subscription eligible for publication notifications (§3.15.2).

The local UAT environment enables the test-loopback opt-in through
`SUBSCRIPTIONS_ALLOW_LOOPBACK_HTTP=1` in `scripts/uat-start.sh`, so a scenario can run a
disposable callback server on `127.0.0.1` over plain `http`. A subscriber can register such a
URL there, then call the verification route with its management token. Production does not set
the flag, so only public HTTPS callbacks are accepted and contacted.

### 3.15.2 Signed publication notifications

When a provider publishes a new rulebook version, the committed `rulebook.published` event
(§3.4.1) is durably mapped to one outbox job per **active, verified** subscription of the same
rulebook that was registered under the current deployment key and existed no later than the
publication instant. Pending, revoked, unrelated-rulebook, later-registered and stale-key rows
are never enqueued, and nothing is delivered for drafts, refreshes, failed publications or an
idempotent re-publish of an already-published version.

Enqueue happens only after the publication transaction commits. It is a bounded SQLite write
that performs no DNS lookup and opens no socket, so the publish response never waits for a
subscriber and a subscriber failure can never roll a publication back. A publication therefore
succeeds even when every subscriber is unavailable: the event remains on the public feed and
the outbox row remains durable.

Delivery is asynchronous and **at-least-once**. An in-process dispatcher (no Redis, broker or
extra service) leases due jobs, invokes the single-attempt signed deliverer exactly once per
claim, and records success or a typed failure. A retry uses the immutable event row, so the
`X-AttestBook-Event-Id` header, the notification body fields and the per-subscription identity
are identical across attempts; only the retry timestamp (and therefore the signature over it)
changes. A subscriber must deduplicate by event ID and may reconcile through the public event
feed.

Retries are bounded and deterministic in policy, not in timing:

| Bound | Default | Behaviour |
| --- | --- | --- |
| Backoff | 1 s base, 60 s cap | Exponential per claimed attempt with 50–100 % jitter; the next attempt is never earlier than half the exponential delay |
| Attempts | 8 | A failed job becomes `failed` with `terminalReason: "max_attempts"` |
| Age | 1 h from enqueue | No job is claimed after the age cap; it becomes `failed` with `terminalReason: "max_age"` |
| Lease | 15 s | A claimed job is recovered after its lease expires, so a crashed process does not strand it |
| Pending outbox | 10,000 jobs | New eligible jobs beyond the bound are dropped with a count-only server warning; subscribers reconcile through the event feed |
| Status retention | 7 days | Delivered/failed rows are pruned after this window |

A transport failure (`timeout`, `dns_failure`, `network_failure`) and a `5xx` answer are
retried. A `2xx` answer is success regardless of its body. A `4xx` answer, a `3xx` redirect, a
blocked or non-public target, an oversized response and a subscription that is no longer
active, verified or bound to the current key are terminal (`non_retryable` or
`subscription_ineligible`) and never loop. Every failure is typed and none is reported as
success.

The outbox is restart-safe. A job row is the single permanent record for its
`(event, subscription)` pair, so re-enqueueing the same event is a no-op. A dispatcher that
finds an expired attempt lease reclaims it and retries; a reconciliation cursor over the
immutable event feed catches an event whose enqueue did not complete before a crash. Neither
path creates a second permanent job. The deployment is the documented single-writer SQLite
process ([`docs/architecture.md`](architecture.md) §10); the lease still makes an accidental
concurrent claim safe.

A subscription that is revoked or otherwise becomes ineligible after a job is enqueued is
re-read immediately before its attempt: no callback is contacted and the job becomes
`failed`/`subscription_ineligible`. Events published while a subscription is still `pending`,
revoked or disabled are not delivered retroactively; after it becomes active the subscriber
reads the public `GET /api/v1/rulebooks/{rulebookId}/events` feed and reconciles by event ID.
The subscriber's bounded delivery status (§3.15.3) shows which recent events were delivered.

The notification body is the stored event projection, so its `id` is the same stable event id
`GET /api/v1/rulebooks/{rulebookId}/events` serves:

```json
{
  "id": "<stored event id>",
  "format": "attestbook.rulebook-publication-event@1",
  "type": "rulebook.published",
  "rulebookId": "<rulebook id>",
  "version": "1.0.1",
  "contentDigest": "<64 lowercase hex characters>",
  "publishedAt": "2026-01-01T00:00:00.000Z"
}
```

The body is bounded to 16 KiB and carries no draft content, provider identity, credential or
audit metadata. A delivery POST uses these headers:

| Header | Value |
| --- | --- |
| `Content-Type` | `application/json` |
| `X-AttestBook-Event-Id` | the stored event id |
| `X-AttestBook-Event-Type` | `rulebook.published` |
| `X-AttestBook-Timestamp` | the delivery attempt timestamp, ISO 8601 |
| `X-AttestBook-Signature` | `v1=<lowercase hex HMAC-SHA-256>` |

The signature commits to the exact body plus the timestamp and event id. The canonical signing
input is UTF-8 with a single LF between four lines and no trailing newline:

```text
attestbook.webhook-signing-input@1
<X-AttestBook-Timestamp>
<X-AttestBook-Event-Id>
<lowercase hex SHA-256 of the exact request body bytes>
```

`X-AttestBook-Signature` is `v1=` followed by `HMAC-SHA-256(webhookSecret, canonicalInput)` in
lowercase hex. A verifier must compare it in constant time and should reject a timestamp outside
a small tolerance window; the event id duplicates the body id so it can be used as a
deduplication key even before parsing. `verifyWebhookSignature` in
`src/subscriptions/delivery.ts` is the reference implementation.

Fixed test vector (not a production secret):

```text
deployment key (UTF-8, 32 bytes): 0123456789abcdef0123456789abcdef
subscription id:                  subscription-vector-1
webhook secret:                   atw_vIq7G8hzcwa9GKj68f2X2oYNzSGoDb1D_14l3zDjyT4
event id:                         event-vector-1
timestamp:                        2026-01-01T00:00:00.000Z
body:                             {"id":"event-vector-1","format":"attestbook.rulebook-publication-event@1","type":"rulebook.published","rulebookId":"rulebook-vector","version":"1.0.1","contentDigest":"aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa","publishedAt":"2026-01-01T00:00:00.000Z"}
canonical signing input:          attestbook.webhook-signing-input@1
                                  2026-01-01T00:00:00.000Z
                                  event-vector-1
                                  bbbdcc887cc99b8977e2475dd4c01f4a300726175dfda68011b9affa6e33b6a6
signature header:                 v1=380592345e511699613ac27b3c6caf870fea8948c21e676652945021de963ed0
```

The destination is re-validated and resolved at send time exactly like verification
(§3.15.1): every resolved answer must be public, the connection is pinned to the validated
address, redirects are never followed, and the lookup, connection and request share a
five-second deadline with an 8 KiB response cap.

`SUBSCRIPTION_WEBHOOK_SIGNING_KEY` is an unpadded base64url string of at least 32 bytes. It must
stay stable for the deployment, because a changed or rotated key changes every derived webhook
secret and invalidates previously issued ones; subscriptions bound to an earlier key are skipped
rather than sent notifications they cannot verify. The key is never returned by the API or
logged.

### 3.15.3 Subscription delivery status

`GET /api/v1/subscriptions/{subscriptionId}/deliveries` reads the bounded delivery history of
exactly one subscription. It requires the same per-subscription
`Authorization: Bearer <managementToken>` credential as the other management routes; a provider
bearer token, the administrator session cookie and every other credential have no authority
here. A missing, malformed, invalid or foreign token and an unknown subscription id answer the
same `401`; a revoked subscription answers `404`. The response is `Cache-Control: no-store`.

`limit` defaults to 20 and is bounded at 100; `offset` defaults to 0. Entries are newest first
and the response is a bounded page:

```json
{
  "data": [
    {
      "eventId": "<stored event id>",
      "status": "delivered",
      "attempts": 2,
      "createdAt": "2026-01-01T00:00:00.000Z",
      "updatedAt": "2026-01-01T00:00:02.000Z",
      "nextAttemptAt": null,
      "lastAttemptAt": "2026-01-01T00:00:02.000Z",
      "lastErrorCategory": null,
      "terminalReason": null,
      "deliveredAt": "2026-01-01T00:00:02.000Z",
      "failedAt": null
    }
  ],
  "pagination": { "limit": 20, "offset": 0, "total": 1 }
}
```

`status` is `pending`, `delivered` or `failed`. A pending job reports its next attempt instant;
a terminal one reports `deliveredAt` or `failedAt`. `lastErrorCategory` is one stable typed
reason (`timeout`, `network_failure`, `dns_failure`, `unexpected_status`,
`redirect_not_followed`, `blocked_target`, `response_too_large` or
`subscription_not_eligible`). `terminalReason` is `max_attempts`, `max_age`, `non_retryable`,
`subscription_ineligible` or `event_missing`.

The view never contains the callback URL, the management token, a token hash, a response body,
a client address or another subscriber's rows. It reports bookkeeping only; the notification
payload is read from the public event feed, and deduplication remains the subscriber's
responsibility.

| Subscription management | revoked subscription read or verification | `404` | `not_found` |
| Callback verification | wrong/expired challenge, redirect, non-`200` status, invalid or oversized acknowledgement, or a refused non-public target | `409` | `verification_failed` |
| Callback verification | a different verification handshake is already in progress | `409` | `conflict` |
| Callback verification | DNS failure, connection failure or timeout reaching the callback | `502` | `callback_unreachable` |
| Callback verification | per-subscription verification attempt bound exceeded | `429` | `rate_limited` |
| API wiring | registry, validation, issuer discovery, issuer fixtures, verifier policy resolver, capture explorer or subscription service not configured | `503` | `registry_unavailable` / `validation_unavailable` / `capture_unavailable` / `subscription_unavailable` |
| Administrator login | configuration absent, partial, invalid or its provider missing | `503` | `auth_unavailable` |
| Schema registration | deployment has no valid `PUBLIC_BASE_URL`, so no canonical hosted URL can be issued | `503` | `public_base_url_unavailable` |
| API | unexpected failure | `500` | `internal_error` |

Unknown routes under any path answer `404` with `not_found` and the same envelope. The
mapping is implemented once in `src/api/errors.ts`; the OpenAPI document references the same
`ErrorEnvelope` component for every error response. A `401` from a protected route also carries
the RFC 6750 challenge `WWW-Authenticate: Bearer realm="attestbook"`, whatever credential was
attempted, so the failure does not disclose which credential path was used; the session-only
`/auth/me` route deliberately does not advertise a bearer challenge. A `401` from a subscription
management route likewise carries no provider bearer challenge, because the credential there is
the subscription's own management token. A refused cookie state change answers `403
csrf_failed` and carries no challenge.

## 5. Authentication and authorization

The complete security model, including token lifecycle, the operation/ownership matrix and
secret-handling guarantees, is documented in [`docs/security.md`](security.md). This section
summarizes the HTTP contract.

- Reads are public, mirroring TS11's public-read requirement and the registry service's
  public read surface. The two exceptions are the import preview and issuer discovery: both
  make the server perform a bounded outbound fetch under the untrusted-import controls, so
  their HTTP routes require a provider credential even though they write nothing.
- Writes, the import preview and issuer discovery accept a provider bearer token or the
  administrator browser session (issue #89). Tokens use the `att_` prefix and are stored only
  as SHA-256 hashes; the raw secret is returned once by operator provisioning, which is not an
  HTTP route. The API never echoes a token, and a session never mints, returns or stores one.
  The route table's `security` flag gates authentication centrally, before any request body is
  read, so a protected operation cannot forget the check. Missing, malformed, unknown and
  revoked credentials all answer `401` with `unauthorized` and the bearer challenge. A present
  but invalid bearer is never downgraded to the cookie session, and a cookie state change
  without its CSRF token answers `403 csrf_failed`.
- Ownership is enforced by the registry service on the stored resource, not by the route.
  The publish route additionally authenticates and checks ownership before its idempotent
  replay check so a foreign or missing token cannot get a write-shaped success or probe
  version existence.
- `metadata`, `provenance` and `importKey` are registry-internal. The create handler
  projects a whitelist of public fields, so a caller cannot inject them even though the
  service type accepts them internally, and a rulebook is always attributed to the
  authenticated provider.
- The optional administrator browser session is a second transport for the same provider
  actor, not a third authority. It is cookie based, bound to an existing provider, and neither
  requires nor mints a bearer token: the session resolves directly to the trusted actor the
  registry accepts and never issues a synthetic token. Its write authority is exactly the
  bound provider's, so the operation matrix in [`docs/security.md`](security.md) §3.1 is the
  same for both transports apart from the cookie's CSRF requirement.
- Anonymous subscription registration needs no credential at all. Its management and
  verification routes accept only the subscription's own management token in the
  `Authorization` header (the same header name as a provider token, but a different credential
  and a different operation set): the provider token, session cookie and CSRF token have no
  authority there, and the subscription token has no authority on any registry or provider
  route. Management and verification failures are uniform `401`s without a provider bearer
  challenge and without disclosing whether the id exists.

Generic API rate limiting, token expiry/rotation and provider-administration routes are not
implemented in Phase 1; administrator login failures are rate limited separately and anonymous
subscription registration has its own per-client quota
([`docs/security.md`](security.md) §2.1, §3.1 and §8).

## 6. Idempotency policy

Phase 1 supports idempotency where the domain provides a deterministic identity; it does
**not** implement a generic `Idempotency-Key` request store.

| Operation | Policy |
| --- | --- |
| `POST /api/v1/imports` | **Idempotent for unchanged content.** Each source entry has a deterministic import identity, so re-importing the same normalized entry is a `200` with disposition `unchanged` and no write. Changed content is reported as a `conflict` and never overwrites local or published content. A URL preview's `retrievedAt` changes between calls, but that is provenance, not identity. |
| `POST .../versions/{version}/publish` | **Idempotent replay while the version is published:** the same call returns `200` and the published representation, and does not create another version. A version superseded to `historical` answers `409 immutable` and is never resurrected. The post-commit delivery enqueue is keyed by `(event, subscription)`, so replay or reconciliation never creates a second outbox job; the notification itself is at-least-once over retries. |
| `POST .../versions/{version}/refresh` | **Idempotent for unchanged content:** re-snapshotting an unchanged working copy returns `200` with the same digest and writes nothing. A changed working copy produces a new digest; a published/historical version answers `409 immutable`. |
| `GET .../versions/{version}/compare` | Read-only; safe to retry. |
| `GET .../versions/{version}/publication-readiness` | Read-only; safe to retry. |
| `POST /api/v1/rulebooks` | **Not idempotent.** There is no server-side deduplication of authored rulebooks; a retried request can create a second draft. Clients that need a stable identity should use the import path or reconcile by `id`. |
| `PUT /api/v1/rulebooks/{rulebookId}/draft` | **Idempotent full replacement.** The same authorized document produces the same working copy; a retried request does not create a duplicate rulebook. A published/historical rulebook still answers `409 immutable`. |
| `POST /api/v1/rulebooks/validate-draft` | Read-only and side-effect free; safe to retry. |
| `POST /api/v1/rulebooks/{rulebookId}/versions` | **Not idempotent.** A duplicate label is `409 conflict`; the client chooses the next label after a conflict. |
| `POST /api/v1/imports/preview` | Read-only and side-effect free, but authenticated because a URL preview performs a bounded outbound fetch; safe to retry. |
| `POST /api/v1/credentials/validate` | Read-only; safe to retry. |
| `POST /api/v1/conformance/runs` | Read-only and side-effect free. The same pinned request returns the same `inputDigest` and `resultReference` when the run is deterministic; a run cut short by a runtime condition returns `deterministic: false` and must be retried. No run is recorded, so there is no server-side history to deduplicate. |
| `POST /api/v1/rulebooks/{rulebookId}/subscriptions` | **Not idempotent.** Each call creates a new pending subscription and mints a new one-time management token; there is no deduplication by callback URL. The per-client quota and per-rulebook bound still apply. |
| `POST /api/v1/subscriptions/{subscriptionId}/verify` | **Idempotent for an active subscription:** a repeat returns `200` with the active representation and contacts no endpoint. On a pending subscription each call is an explicit new handshake with a fresh challenge and a fresh (bounded) outbound request, so it is not a no-op retry. A concurrent handshake answers `409 conflict`. |
| `DELETE /api/v1/subscriptions/{subscriptionId}` | **Idempotent.** After a successful revoke, a repeat with the same valid management token is a no-op `204`; the revoked state and revocation instant are unchanged. Missing, invalid or foreign tokens still answer `401`. |
| `GET /api/v1/subscriptions/{subscriptionId}/deliveries` | Read-only and safe to retry with the same management token; the durable state may advance between reads. |

The import policy is the substantive idempotency mechanism implemented in Phase 1
([`docs/import.md`](import.md) §5). A generic idempotency-key store is deliberately deferred:
it needs a durable request/response store and a retention policy, and must not be invented
as an untested placeholder.

## 7. OpenAPI generation and validation

The OpenAPI 3.1 document is **generated**, not hand-maintained:

- `src/api/routes.ts` declares the route table (`API_ROUTES`), its request/response
  components, security and status codes, and registers those same paths on Hono. The
  handler map is typed `Record<ApiOperationId, ...>`, so a route without a handler is a
  compile-time error.
- `src/api/schemas.ts` defines the request/response shapes with Zod. `componentJsonSchema`
  converts each to JSON Schema 2020-12 for OpenAPI 3.1, and the same schemas validate the
  actual response bodies in the contract tests.
- `src/api/openapi.ts` builds `components.schemas`, `paths` and `securitySchemes` from those
  two sources.

The same generated document is served at the public, unauthenticated, unversioned
`GET /openapi.json` endpoint, so clients and documentation tools can discover the contract
without checking out the repository. The route is registered in `src/app.ts` and is
deliberately **not** a member of `API_ROUTES`: `/api/v1` carries the product API's major
version, while the documentation endpoint describes it. It reads no deployment secret and
builds no second contract; unknown routes keep the typed `not_found` envelope.

Validation runs in two places:

1. `src/api/openapi.test.ts` (in the `test` job) validates the generated document against
   the **official OpenAPI 3.1 JSON Schema**, compiles every component as JSON Schema
   2020-12, and compares the documented operations with `app.routes` from the app the tests
   exercise (excluding the unversioned `/openapi.json` documentation route). It also checks
   that every path template parameter is declared, that every protected operation declares
   the bearer and session alternatives, and that every protected non-GET operation documents
   the `X-CSRF-Token` header. `src/api/openapi-route.test.ts` requests the live endpoint
   without credentials, checks the JSON media type and parity with
   `buildOpenApiDocument()`, validates the served document against the same official schema,
   and confirms that an unknown `/api/v1` route keeps its typed 404.
2. `bun run openapi:check` (in the `openapi` CI job) performs the document/schema validation
   standalone, so a broken contract fails CI even if a route test is skipped.

The official schema is vendored at `src/api/oas-3.1-schema.json` from
<https://spec.openapis.org/oas/3.1/schema/2022-10-07> (OpenAPI Specification 3.1.0,
Apache-2.0). The loader rewrites its four `$dynamicRef: "#meta"` references to the
equivalent static `$defs/schema` reference because Ajv 8.20.0 resolves that dynamic
reference to the document root; the vendored bytes themselves are unchanged. This is a
validator workaround, not a contract change.

### Interactive reference

`GET /docs` renders the same generated document through Scalar, bundled with the UI build
(`ui/docs.html` and `ui/src/docs/main.ts`) rather than loaded from a CDN. The page is
anonymous and static: it carries only the same-origin `/openapi.json` path in
`data-openapi-url`, and the entry configures Scalar with telemetry, default remote fonts, the
dashboard toolbar, the hosted client and the Ask AI agent disabled. Scalar fetches the
document at runtime, so a reverse proxy with a custom public host needs no extra
configuration and the reference cannot drift from the served contract.
`src/api/docs-route.test.ts` covers the entry point, anonymous access, local-only assets,
the same-origin contract reference and the JSON 404 when no UI build is served;
`ui/e2e/docs.spec.ts` renders the built page, checks a real generated operation with its
query parameters and authentication schemes, and reloads it while rejecting any third-party
request. The reference documents the product API only; the TS11 catalogue API is not part of
it.

## 8. Verification

Run the relevant checks from the repository root:

```
bun run openapi:check   # generated OpenAPI 3.1 document validates
bun test src/api/openapi-route.test.ts  # public JSON endpoint, media type, parity and 404
bun test src/api/docs-route.test.ts  # public /docs entry point and same-origin contract
bun test src/api        # contract, success and error coverage
bun run test:e2e        # Playwright UI flows, including the rendered reference at /docs
bun test src/auth       # administrator login configuration, sessions, limits and origins
bun test src/api/auth.test.ts  # administrator login/session HTTP contract
bun test src/api/session-writes.test.ts  # session-authorized writes, CSRF and bearer precedence
bun test src/discovery  # discovery extraction, bounds and association
bun test src/fixtures   # fixture synthesis, grounding and negative cases
bun test src/verifier   # typed verifier constraints and OpenID4VP-aware mappings
bun test src/comparison # headless-wallet comparison contract and bounds
bun test src/conformance # reproducible result references and failure classification
bun test src/api/verifier.test.ts  # verifier-constraint HTTP contract
bun test src/api/comparison.test.ts  # comparison HTTP contract and pin linkage
bun test src/api/conformance.test.ts  # conformance HTTP contract, repeats and classification
bun test src/subscriptions # callback URLs, tokens, storage, quota, verification and activation
bun test src/api/subscriptions.test.ts  # registration/management/verification HTTP contract
bun run check           # formatting, lint, strict typecheck and all tests
```

The API tests use real temporary SQLite databases, real registry services, the real import
pipeline (offline JSON sources only) and a genuinely signed SD-JWT VC fixture. The
administrator tests use real Argon2id hashes, temporary databases and injected clocks for
deterministic expiry. Discovery tests use an injected transport and DNS resolver, so no test
performs a real network request. The subscription tests patch the process `fetch` to prove
registration performs no request, inject a fake resolver and transport for every verification
path (unsafe destinations, private/mixed DNS answers, rebinding, wrong, oversized and expired
acknowledgements, redirects, timeouts and the attempt bound), and reopen the SQLite file to
prove the subscription, its token hash and its activation persist.
`src/subscriptions/verification-http.test.ts` runs the real transport against a disposable
loopback HTTP server for the successful handshake, a wrong challenge, a redirect, a timeout
and the response cap. They do not claim coverage of general API rate limits or
provider-management routes. The catalog UI has its own component and browser tests described
in [`docs/ui.md`](ui.md).

## 9. Limitations and next slices

- Catalogue pagination is applied in memory after filtering; versions and attestations are
  returned in full. A paginated store query is a later registry slice.
- The interactive reference at `/docs` needs the built UI (`dist/ui/docs.html`); a source
  checkout without a UI build keeps the JSON 404 for that path, like the other UI routes. It
  renders the generated product contract and adds no hand-written API content.
- No generic `Idempotency-Key` store, no request-body content-type enforcement beyond JSON
  parsing, and no HTTP rate limits for reads, preview, import or discovery. Administrator
  login failures and anonymous subscription registrations are bounded separately (§3.11 and
  §3.15). Rate limiting is still missing for the outbound-fetch routes, so an authenticated
  provider can repeat a bounded fetch; the import and discovery services' own size, time,
  redirect and fan-out limits still apply to every call. General rate limiting,
  token expiry/rotation and provider-administration routes remain future hardening work
  documented in [`docs/security.md`](security.md) §8.
- Publication delivery is at-least-once with a durable SQLite outbox and bounded retries
  (§3.15.2); it is not exactly-once, so subscribers must deduplicate by event ID. The
  dispatcher is one in-process timer on the documented single-writer deployment
  ([`docs/architecture.md`](architecture.md) §10), not a broker or a multi-node scheduler.
  Enqueues beyond the bounded outbox are dropped with a count-only warning, terminal delivery
  rows are retained for seven days, and events published while a subscription was pending or
  revoked are not replayed; a subscriber reconciles them through the public event feed. The
  retry constants are compiled-in defaults rather than deployment configuration in this slice.
  The registration quota is in-process, resets on restart and is keyed per IPv4 address or
  IPv6 /64; behind a reverse proxy all clients share the proxy socket address because
  forwarding headers are deliberately not trusted. The verification attempt window and the
  challenge expiry are durable, but subscriptions themselves never expire and there is no
  operator cleanup, so a full per-rulebook bound stays full until subscribers revoke rows.
- The administrator login is one environment-configured account with no MFA, self-service
  password change or account management API; rotating the password means changing
  `ADMIN_PASSWORD_HASH` and restarting. The failure limiter is in-process and resets on
  restart.
- Import previews expose a projection (no internal canonical document) and do not persist a
  preview; an import re-runs the preview under the same controls.
- Discovery is read-only: it does not persist discovered issuers, metadata snapshots or
  manual mappings, and it does not fetch exposed references or verify signed metadata
  ([`docs/discovery.md`](discovery.md) §1 and §9).
- Issuer fixtures are unsigned claim payloads, not issued credentials. They are synthesized
  from caller-supplied, integrity-verified schema documents and only within the supported
  JSON Schema subset; compilation and evaluation run in the shared resource-bounded sandbox,
  and the route fetches no schema, signs nothing and persists nothing
  ([`docs/fixtures.md`](fixtures.md) §2.4, §3 and §6).
- Verifier constraints are typed attribute and format constraints plus explicitly partial
  OpenID4VP DCQL mappings. The route produces no presentation request, proof, trust decision
  or protocol result, reports every mapping it cannot express, and inspects only
  caller-supplied, integrity-verified schema documents within hard bounds
  ([`docs/verifier.md`](verifier.md) §2.1, §5 and §6).
- Conformance runs are not persisted: `POST /api/v1/conformance/runs` recomputes the
  deterministic result on every call and returns a content-addressed `resultReference`
  instead of a stored run resource. External orchestration keeps the run history. A run cut
  short by a runtime condition returns `deterministic: false` with its
  `environmentConditions` and must be retried rather than compared as drift
  ([`docs/conformance.md`](conformance.md) §4 and §9).
- Validation results are returned synchronously and are not persisted
  (`GET /api/v1/validations/{id}` does not exist in this slice; the specification lists it as
  a suggested resource, not an implemented one).
- Capture routes are implemented only for the deterministic mock source. The explorer keeps
  its normalized evidence and recorded correlations in memory, never fetches an external
  artifact reference, does not unpack a captured presentation submission and does not persist a
  run history. A live `capture-issuer`/`capture-verifier` connector remains unimplemented and
  absent rather than present as a placeholder.
- Headless-wallet comparison evidence is a read-only projection over a recorded capture
  correlation and the caller's external wallet observation. It orchestrates no wallet, does
  not verify the observation, does not diff two credentials or rulebook versions, and
  persists no comparison
  ([`docs/headless-wallet-comparison.md`](headless-wallet-comparison.md) §8).
- The TS11 catalogue API remains unimplemented and is absent from the OpenAPI document rather
  than present as a placeholder.
