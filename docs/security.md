# AttestBook API security model — authentication, provider authorization and secret handling

**Status:** Phase 1 implementation and verification of the write-API security model for
[issue #35](https://github.com/ForkbombEu/credimi-attestbook/issues/35), reviewed by the Phase 6
security audit in [issue #52](https://github.com/ForkbombEu/credimi-attestbook/issues/52). It
documents what the server enforces, not a future design. It is **not** a TS11 normative
authorisation mechanism: TS11 §5.2.2 leaves that unspecified, so AttestBook uses the
provisional product model of decision D-10. The cross-cutting threat model, SSRF/recursion
verification, retention policy and residual-risk register are in
[`docs/security-threat-model.md`](security-threat-model.md).

**Authoritative spec:** [`docs/specification.md`](specification.md) §13 (public API) and §15
(security requirements).
**Related:** [`docs/api.md`](api.md) (HTTP contract and error table),
[`docs/registry.md`](registry.md) §5 (service-layer ownership),
[`docs/architecture.md`](architecture.md) §6 (authorization and ownership design) and
[`docs/implementation-plan.md`](implementation-plan.md) D-10 (provisional bearer
authentication).
**Implementation:** `src/api/routes.ts` (one route table and the central bearer check),
`src/api/errors.ts` (typed error mapping), `src/app.ts` (HTTP assembly),
`src/registry/registry.ts` (ownership enforcement), `src/registry/bootstrap.ts` (operator
provisioning), `src/registry/tokens.ts` (token primitives), `src/auth/` (environment
administrator login, sessions, rate limiting and origin checks) and
`migrations/0004_admin_sessions.sql` (hashed session rows).

## 1. Trust boundaries and actors

| Actor | Credentials | Authority |
| --- | --- | --- |
| Anonymous reader | none | Public catalogue, attestation, schema-reference, version, snapshot, stored credential-schema metadata/content and health reads; structural credential validation. |
| Provider account | Provider bearer token (`Authorization: Bearer att_…`) | Create and mutate only the rulebooks owned by that provider; import drafts owned by that provider; preview imports; discover issuer metadata. |
| Administrator (browser) | Environment-configured username and Argon2id password hash; opaque session cookie plus its session-bound CSRF token | Authorize the same protected provider write routes a bearer token authorizes, as the bound **existing** provider (issue #89). The session resolves to the same trusted actor as a token; every state-changing cookie request must echo `X-CSRF-Token`. It does not create a provider or mint or expose a bearer token. |
| Operator | Out-of-band deployment access | Provision a provider and its first token, configure the optional administrator login, audit inspection and deployment configuration. Nothing in the HTTP API performs provider administration. |
| Remote import or issuer source | none | Untrusted input; bounded and validated by the import/discovery pipelines, never trusted for provider identity or publication authority. |

Writes are authenticated; reads are deliberately public, mirroring TS11's public-read
expectation. Provider identity is never inferred from a remote URL, a `rulebookURI`, an
import source, issuer metadata or a request body.

## 2. Authentication

Provider bearer tokens and the administrator browser session are two credential paths to the
same provider actor (issue #89). Both are resolved once per request, before any handler runs,
and the result is an `AuthenticatedActor` bound to one provider; the registry service accepts
only that actor and never a raw token. A request resolves its actor as follows:

- A present `Authorization` header is authoritative. A valid bearer token resolves to its
  provider with `authMethod: "bearer"`. A malformed, unknown or revoked bearer answers `401`
  and **never** falls back to a cookie session, so a client that supplies a token cannot
  accidentally act as the browser's logged-in user.
- Otherwise, a valid `attestbook_admin_session` cookie resolves to the configured provider
  with `authMethod: "session"`. A state-changing request must also echo the session-bound
  CSRF token in `X-CSRF-Token` (see §2.1); a missing or wrong token answers `403 csrf_failed`
  and changes nothing.
- With neither credential the protected route answers `401`.

The protected-route set, ownership checks, provider attribution and audit semantics are the
same for both paths: the session only changes how the actor is proved, never what it may do.

- A write request presents `Authorization: Bearer <token>`. The scheme is case-insensitive;
  exactly one non-empty token is accepted. No token is accepted from a query string, cookie
  or body.
- Tokens are generated by the operator-only `provisionProvider` path (or `issueToken` for an
  authenticated provider) with the `att_` prefix and 256 random bits. Only a SHA-256 hash is
  stored in `auth_tokens`; the raw secret is returned exactly once and cannot be recovered
  from the database or the API. The API never echoes a token.
- `authenticate` resolves the hash, rejects an unknown or revoked token, and returns an actor
  bound to the token's provider. Missing, malformed, unknown and revoked credentials are
  indistinguishable: every protected route answers `401` with the `unauthorized` envelope and
  `WWW-Authenticate: Bearer realm="attestbook"`. This avoids a token-validity oracle.
- Token revocation is idempotent and provider-scoped. Token expiry and a rotation policy are
  not implemented in Phase 1 (§8).

### 2.1 Administrator browser session

The optional single-administrator login (issue #88) keeps its own credential path in
`src/auth/` and `admin_sessions`; it never creates a provider, mints a bearer token, stores an
API token in the session or changes the bearer checks above.

- **Configuration.** `ADMIN_USERNAME`, `ADMIN_PASSWORD_HASH` and `ADMIN_PROVIDER_ID` must be
  set together. The hash must be an Argon2id PHC string with at least 19 MiB of memory and
  two passes; a plaintext password is never accepted. The provider id must identify an
  existing provider and is re-checked on every login attempt. A missing, partial, invalid or
  unresolvable configuration leaves the login endpoints answering `503 auth_unavailable` while
  the public API and bearer writes continue to work. Startup logs the non-secret reason only.
- **Verification and non-enumeration.** The username is compared in constant time and the
  Argon2id verification always runs, so an unknown username and a wrong password take the same
  path. Both answer the same generic `401 unauthorized` body and neither logs the submitted
  values. Passwords longer than 1024 characters are rejected without hashing.
- **Opaque server-side sessions.** Login mints 256 random bits, sets them in the
  `attestbook_admin_session` cookie and stores only their SHA-256 hash in `admin_sessions`.
  Cookie attributes are `HttpOnly`, `SameSite=Lax`, `Path=/`, an eight-hour absolute
  `Max-Age`, and `Secure` when the request is HTTPS directly or through a proxy that sets
  `X-Forwarded-Proto: https`. The identifier is never accepted from a URL or request body and
  is never returned in a response body.
- **Bounded lifetime, revocation and rotation.** `expires_at` is an absolute bound checked on
  every read. Logout sets `revoked_at` server-side, so replaying the cookie fails even if a
  client keeps it; repeated logout is idempotent. Every successful login mints a new
  identifier and revokes the session the browser presented, which defends against session
  fixation. Each session also stores an `auth_fingerprint` over the configured username,
  provider and password hash, so rotating any of those invalidates outstanding sessions.
- **CSRF and cross-origin.** `SameSite=Lax` withholds the cookie from cross-site POSTs. Login
  and logout also require a missing `Sec-Fetch-Site` or `same-origin`/`none`, and a missing
  `Origin` or one equal to the effective request origin (forwarded headers honoured); they
  answer `403` otherwise. Login accepts only `Content-Type: application/json`, which a
  cross-site HTML form cannot send without a CORS preflight. The login and logout endpoints
  add no audit rows (neither successes nor failures).
- **Session-bound CSRF token for writes (issue #89).** Every login mints a 256-bit random CSRF
  token, returned once in the login body as `csrfToken` and stored on the session row; a fresh
  login always mints a fresh token with the fresh session. `GET /api/v1/auth/me` also returns
  the live token so a reloaded page keeps working. Every state-changing request that
  authenticates with the cookie must send that token in `X-CSRF-Token`; the check is a
  constant-time comparison and a missing or wrong value answers `403 csrf_failed` without
  touching the database. The token is not an authenticator on its own — it is accepted only
  together with the cookie, which another site cannot read — and it is never put in a cookie,
  URL or log. It is stored on the session row (rather than hashed) because `GET /auth/me` must
  return it to a cookie-authenticated caller; on its own it grants no authority. Logout
  requires it when a live session cookie is present while remaining idempotent when there is
  nothing to revoke. A session row created before the column existed is backfilled with a
  random token that `/auth/me` returns, so it keeps working. Login itself (environment
  credentials, JSON body, same-origin) and its rotation path keep the origin and content-type
  controls rather than a bound token, because the credential being proved is in the body, not
  the cookie.
- **Rate limiting and parallel attempts.** Login failures are bounded in-process: five per
  account and twenty per client address in a fifteen-minute sliding window, answering
  `429 rate_limited` with `Retry-After`. An attempt reserves its failure slot before the
  Argon2id check in one synchronous step, so overlapping requests cannot all pass the bound
  before any of them is counted. At most four password checks run concurrently; further
  concurrent attempts answer `429` without touching the CPU or memory of a hash. A successful
  login clears both keys; the account key is case-folded so case variants do not reset the
  budget. The limiter is not persisted and resets on restart, and it does not rate-limit
  bearer-token API traffic.
- **Provider binding only.** `/api/v1/auth/me` returns the public provider projection
  (`id`, `name`, `createdAt`), the session expiry and the session CSRF token. It exposes no
  publication authority, metadata, password hash or bearer token. The browser stores no
  session identifier or password in `localStorage`/`sessionStorage`; the cookie is the only
  client-side credential, and the CSRF token only accompanies it.
- **Browser UI transport (issue #91).** The catalogue, rulebook detail, playground and
  capture explorer stay anonymous. The rulebook editor's create/save and lifecycle actions
  and the protected capture correlation use only the session cookie and `X-CSRF-Token`; the
  UI never asks for, stores or sends a provider bearer token for them. An anonymous deep link
  renders a sign-in panel whose validated same-origin `next` target returns to that view. A
  `401` or a `403 csrf_failed` from a write keeps the editor or correlation form mounted and
  requests re-authentication inline rather than discarding the unsaved state; a `403
  forbidden` ownership refusal shows the server's message instead, because re-signing in
  cannot grant access to another provider's resource. Headless clients keep the bearer
  transport described above.

## 3. Authorization and provider ownership

Every mutation loads the stored resource and requires
`rulebook.provider_id === actor.providerId`. The check is in the registry service, so it
applies to every caller and cannot be forgotten by a route handler; the HTTP layer does not
accept an ownership claim from the request. A denied mutation answers `403` with the
`forbidden` envelope and leaves the database unchanged.

The following rules implement that model:

- **Create.** `POST /api/v1/rulebooks` has no `providerId` member. The handler projects a
  whitelist of public fields and the service attributes the rulebook to the authenticated
  actor. `metadata`, `provenance` and `importKey` cannot be injected through the API.
- **Version mutations.** Creating, refreshing and publishing a version first requires the
  actor to own the stored rulebook. The publish handler additionally authenticates and checks
  ownership **before** its idempotent replay check and before looking a version up, so a
  foreign provider cannot obtain a replay success or probe version existence.
- **Imports.** `RulebookImporter.import` authenticates before any network fetch and scopes the
  deterministic import identity and `findImportedRulebook` to the authenticated provider.
  Imported drafts are owned by the importing provider; another provider importing the same
  source gets its own rows and cannot read or mutate the first provider's internal import
  identity.
- **Public reads.** Provider, rulebook, attestation, schema-reference, version, snapshot,
  digest, publication-export, export-manifest and capture-explorer reads need no token,
  including working drafts, by design. The read-shaped routes that require authentication are
  the import preview and issuer discovery (both perform a bounded outbound fetch under the
  untrusted-input controls) and capture correlation (it overwrites the correlation every
  reader sees).
- **Provider administration.** Provider creation, token issuance for a provider without a
  token and audit inspection are operator actions. No HTTP route exposes
  `provisionProvider`.

### 3.1 Operation matrix

| Operation | Auth | Ownership rule | Denial |
| --- | --- | --- | --- |
| `GET /health` | no | n/a | n/a |
| `POST /api/v1/auth/login` | environment credentials | Binds the configured existing provider; never creates a provider or mints a token; returns the session CSRF token | `401` generic; `403` cross-origin; `429` rate limited; `503` unconfigured |
| `GET /api/v1/auth/me` | session cookie | Resolves only its own live session; returns the public provider projection and the session CSRF token | `401` for missing, expired or revoked sessions |
| `POST /api/v1/auth/logout` | session cookie + CSRF token | Revokes its own session; idempotent; a live session requires its CSRF token, an absent one needs none | `403` cross-origin or `csrf_failed`; `204` when there is nothing to revoke |
| `GET /api/v1/rulebooks`, `GET /api/v1/rulebooks/{id}` | no | n/a | `404` for an unknown id |
| `GET /api/v1/schema-documents`, `GET /api/v1/schema-documents/{documentId}` | no | Public stored-schema metadata only; canonical URL built from configured `PUBLIC_BASE_URL`; provider ownership, provenance and tokens never returned | `404` for an unknown id; `503 public_base_url_unavailable` without a configured origin; `400` for invalid pagination |
| `GET /api/v1/schema-documents/{documentId}/content` | no | Public exact immutable bytes; `Content-Digest`/`ETag` integrity evidence; no write method registered | `404` for an unknown id; `400` for an invalid identifier |
| `GET …/attestations`, `…/schema-references`, `…/versions`, `…/versions/{version}`, `…/content` | no | n/a | `404` for an unknown resource |
| `POST /api/v1/rulebooks` | bearer or session+CSRF | New rulebook is owned by the actor; the body cannot set its provider | `401`; `400` for invalid input |
| `GET /api/v1/rulebooks/{id}/draft` | no | Public working-copy projection; no internal metadata | `404` for an unknown id |
| `PUT /api/v1/rulebooks/{id}/draft` | bearer or session+CSRF | Actor must own the stored rulebook and its working copy must be `draft` | `401`; `403` when foreign; `409 immutable` for published/historical; `400` for invalid input |
| `POST /api/v1/rulebooks/validate-draft` | no | Read-only, pure validation; writes nothing | `400` for a non-JSON body; `413` over the body limit |
| `POST …/versions` | bearer or session+CSRF | Actor must own the stored rulebook | `401`; `403` when foreign; `409` for a duplicate label or immutable state |
| `POST …/versions/{version}/publish` | bearer or session+CSRF | Actor must own the stored rulebook; ownership is checked before replay and version lookup | `401`; `403` when foreign; `404` only for the owner; `409` for stale or immutable state |
| `POST /api/v1/imports/preview` | bearer or session+CSRF | No write; the token gates the outbound fetch | `401`; `400`/`422`/`502` for the source |
| `POST /api/v1/imports` | bearer or session+CSRF | Import identity and created drafts are scoped to the actor's provider | `401`; `422` for a refused source |
| `POST /api/v1/issuers/discover` | bearer or session+CSRF | No write and no stored issuer state; the token gates the bounded outbound fetch | `401`; `400`/`422`/`502` for the URL or metadata |
| `POST /api/v1/credentials/validate` | no | Read-only, public by design | `400`/`404`/`503` |
| `GET /api/v1/captures`, `GET /api/v1/captures/{id}` | no | Mock-backed read; normalized metadata plus the redacted projection only, never the raw artifact | n/a |
| `POST /api/v1/captures/{id}/validate` | bearer or session+CSRF | Records an in-memory rulebook correlation visible to every reader; writes no registry data | `401`; `400`; `404`; `409` for evidence that cannot be validated |

Every row marked `bearer or session+CSRF` accepts exactly one of the two credentials; the
session path adds the CSRF header but not a wider authority, so the ownership rule and the
denial statuses are identical. Requesting a protected route with no credential answers `401`
whether the intended credential was a token or a cookie, and the response never says whether a
cookie existed.

The browser editor and the capture correlation form currently hold a provider token: it lives
in the app's React memory for the current page session only, is sent only in the
`Authorization` header of the write request, and is cleared by a full page reload. It is never
placed in a URL, request body, browser storage, log or rendered document. A browser session is
an alternative transport for the same routes; the UI does not use it yet. Draft validation and
credential validation stay public because they write nothing; capture correlation requires a
token because it records server state that every reader sees.

## 4. How protection is enforced

- `src/api/routes.ts` declares every operation once in `API_ROUTES`. Its `security` flag is
  the only list of protected operations; `registerApiRoutes` wraps each protected handler with
  one central check that resolves the trusted actor (bearer token or session cookie) before the
  handler can read a request body or start an outbound fetch. The declared HTTP method decides
  whether a cookie request also needs its CSRF token, so there is no second list of secured
  endpoints that could drift.
- The resolved actor is stored on the request context and read by handlers; no handler parses
  a credential, takes a provider id from input or constructs an actor. The registry service
  exposes `authenticateBearer` for the transport and accepts the already-verified actor
  everywhere else; it never mints or accepts a synthetic token for a browser session.
- The handler map is typed `Record<ApiOperationId, ApiHandler>`, so a declared operation
  without a handler fails the typecheck. The generated OpenAPI document is built from the same
  table, and tests compare it with the routes Hono actually registered.
- Ownership is checked again inside the service (`requireOwnedRulebook`) for every mutation.
  Route-level authentication and service-level authorization are independent layers.
- The shared 4 MiB body limit on `/api/*` runs before route authentication, so a request
  whose declared body exceeds it is rejected with `413` without being read or authenticated.
- Canonical hosted-schema URLs are built only from the operator-configured
  `PUBLIC_BASE_URL` (`src/public-urls.ts`). The request's `Host`, `Forwarded`,
  `X-Forwarded-Host` and `X-Forwarded-Proto` headers are never used to compose a stored,
  published or returned URL, so an attacker cannot make AttestBook mint a URL that later
  appears in a rulebook or snapshot. The configuration accepts only an HTTPS origin (plain
  HTTP only for loopback hosts) without credentials, path, query or fragment, and an invalid
  value fails startup. A missing origin leaves the content route working but makes the
  metadata routes answer an explicit `503 public_base_url_unavailable`.

## 5. Error consistency

Every failure uses the `{ "error": { "code", "message", "details"? } }` envelope. The security
relevant mapping is:

| Condition | HTTP | `error.code` | Additional signal |
| --- | --- | --- | --- |
| Missing, malformed, unknown or revoked bearer token | `401` | `unauthorized` | `WWW-Authenticate: Bearer realm="attestbook"` |
| Missing, unknown, expired or revoked session cookie | `401` | `unauthorized` | the same uniform body and bearer challenge as a failed token |
| Cookie-authenticated protected write without its CSRF token, or with a foreign `Origin`/cross-site `Sec-Fetch-Site` | `403` | `csrf_failed` | none; nothing is written |
| Logout of a live session without its CSRF token | `403` | `csrf_failed` | none; the session is not revoked and the cookie is not expired |
| Cross-origin login or logout (foreign `Origin`/cross-site `Sec-Fetch-Site`) | `403` | `forbidden` | refused before any session is created or revoked |
| Authenticated but not the owning provider | `403` | `forbidden` | none |
| Unknown resource (for the owner) | `404` | `not_found` | none |
| Invalid create/query/body input | `400` | `invalid_request` | none |
| Duplicate label, stale draft, immutable state | `409` | `conflict` / `immutable` | none |
| Body over the limit | `413` | `payload_too_large` | none |
| Unexpected failure | `500` | `internal_error` | none; no internal detail is returned |

Messages are safe to display and never contain bearer tokens, token hashes, credential
material, personal attributes or remote document bytes. The challenge header is documented in
the OpenAPI responses of every protected operation. A protected route answers `401` with the
same body and challenge whether the attempted credential was a bearer token or a cookie, so
the response cannot be used to learn which credential path failed; the session-only
`/auth/me` route answers `401` without the bearer challenge.

## 6. Secret and sensitive-data handling

- Raw bearer tokens are generated once, never persisted in plaintext and never written to an
  error message, response body or log. The database stores only their SHA-256 hash.
- Request headers, bodies and URLs are not logged by the HTTP pipeline. The only request-scoped
  server log is the unhandled-error record in `src/app.ts`, which contains the method, path and
  error class name — never headers, payloads, exception messages or stacks.
- Errors expose stable codes and safe messages only; they do not echo the token that failed
  authentication or any request content.
- The audit trail stores identifiers, actions, field names, version labels and content digests.
  It does not store raw tokens, token hashes, credential material or personal attributes.
- Hosted credential schema metadata is a public projection: identifier, kind, media type,
  SHA-256 digest, SRI pin, creation time and canonical URL. Provider ownership, provenance and
  every token stay registry-internal. The exact document bytes are public by design, because
  the permanent URL is referenced from published rulebooks; they are served without
  re-serialization and never logged.
- The publication export manifest is public, so it carries only a bounded projection of the
  version provenance (`adapter`, `sourceUrl`, `contentDigest`, `retrievedAt`, `profile`,
  `conformance`, `importedAt`). Import-internal redirect chains, optional source labels and
  untrusted envelope metadata are excluded (§15 personal-data minimisation).
- Credential validation is synchronous and nothing is persisted; supplied credentials and
  schema documents are not logged or retained.
- Capture artifacts are untrusted evidence. Normalization segregates an inline artifact out of
  the metadata envelope, the capture explorer never returns those raw bytes (only the redacted
  default-policy projection), and the correlation route refuses an external reference it has not
  fetched as well as non-credential evidence. Correlation requires a provider bearer token
  because it records a correlation every reader sees; the record does not carry the acting
  provider. The source-redacted refusal remains a defensive check that normalization currently
  makes unreachable. The mock explorer keeps evidence and correlations in memory only, logs
  nothing and persists nothing.
- Operator provisioning returns the raw token once to the provisioning call and stores only
  its hash; it is deployment tooling, not an API response, and no secret is committed to the
  repository or CI.

## 7. Audit logging of writes

Privileged mutations write an `audit_log` row with the acting provider (`actor_provider_id`,
`null` for operator provisioning), the action, the entity and safe detail. Rulebook creates,
attestation/schema changes, version creation, version refresh and publication are covered.
Publication records the version, content digest, profile and superseded versions, satisfying
the specification §15 audit requirement for publication operations. Export is a read of an
artifact that was already public; it writes nothing and is not an audited mutation. The audit
trail is not exposed over HTTP; it is read by operators from the database.

## 8. Limitations and non-goals

- **No general HTTP rate limiting.** Login failures are rate limited (§2.1), but an
  authenticated provider can repeat a bounded import fetch or a write at the network level.
  The import pipeline still applies its own timeout, size, redirect and fan-out limits. Rate
  limiting for the remaining routes remains future hardening work.
- **No token expiry or rotation policy.** Tokens are revoked explicitly and provider-scoped.
- **No fine-grained scopes or roles.** Every token of a provider has the provider's full write
  authority; there are no read-only or per-rulebook tokens.
- **Single administrator, no MFA or password change endpoint.** The administrator is one
  environment-configured account; rotating the password means changing `ADMIN_PASSWORD_HASH`
  and restarting (outstanding sessions then fail the fingerprint check). There is no
  self-service password reset, second factor or account management API.
- **The account failure bound can be used for a temporary lockout.** Because the account key
  is the submitted username, anyone who knows it can spend the five-attempt budget every
  fifteen-minute window and keep the single administrator from logging in. This availability
  trade-off is accepted for a single-account deployment; there is no separate unlock path or
  per-client account budget.
- **Behind a reverse proxy the client budget is shared.** The client key is the socket's
  remote address; in a proxy deployment every browser presents the proxy's address, so the
  twenty-attempt client window is effectively global. `X-Forwarded-For` is deliberately not
  trusted as a limiter key.
- **A credential revoked during an import fetch is not re-checked.** The actor is resolved once
  when a protected request enters the route and is passed to the importer, which writes after
  its bounded outbound fetch. Before issue #89 the importer re-authenticated the raw token at
  write time, so a token revoked mid-fetch stopped that write; the actor boundary trades that
  for the request-scoped guarantee. The window is bounded by the fetch timeout (15 s of total
  redirect budget by default), and a token revoked mid-fetch still stops every subsequent
  request. Re-validating the credential before the commit would need a revalidation seam on the
  actor and is deferred.
- **Provider administration is operator-only.** The API does not expose provider provisioning,
  token issuance for a new provider, or provider deletion.
- **Denied attempts are not audited.** The audit trail records successful mutations and token
  lifecycle events, not rejected requests, failed logins or administrator login/logout events.
- **Transport security is deployment-owned.** AttestBook serves HTTP; a deployment must
  terminate TLS in front of it and set `PUBLIC_BASE_URL` to that HTTPS origin. Bearer tokens
  and the session cookie are not meaningful over plaintext transport beyond the documented
  loopback test mode. If the origin is wrong or unset, hosted-schema metadata is unavailable
  rather than silently derived from request headers.
- **The cross-cutting audit is separate.** SSRF and schema recursion, artifact retention,
  the full security test matrix and the residual-risk register are recorded in
  [`docs/security-threat-model.md`](security-threat-model.md); this document covers the
  write-API authentication, provider authorization, error and secret-handling model asked for
  by issue #35. The audit leaves three limitations open and explicit: no general HTTP rate
  limiting (login failure limiting is now separate), no token expiry/rotation and no audit row
  for denied attempts.

## 9. Verification

- `src/api/security.test.ts` exercises the real Hono application and a temporary SQLite
  registry: the exact protected operation set; missing, malformed, unknown and revoked tokens
  on every protected route (`401`, challenge header, no write, no audit event); cross-provider
  version creation and publication (`403`, unchanged state, no version-existence probe);
  provider attribution and internal-field projection on create; public reads and public
  credential validation; no credential in `401` bodies, unhandled-error logs or audit rows.
- `src/registry/authorization.test.ts` covers service-level public reads, cross-provider
  mutation denial for every registry resource, token scoping and unauthorized writes that leave
  the database unchanged.
- `src/api/routes.test.ts` and `src/api/openapi.test.ts` cover the HTTP error envelope,
  auth-before-body-read, cross-provider publish denial and the generated security contract.
- `src/auth/admin-auth.test.ts` covers configuration validation, Argon2id hash acceptance and
  rejection, opaque sessions hashed at rest, provider binding, generic unknown-user versus
  wrong-password outcomes, missing/invalid configuration and missing providers, expiry,
  logout revocation and idempotency, configuration rotation invalidation, login session
  rotation, the failure limiter's parallel reservation and concurrent-check cap, and the
  same-origin/proxy checks.
- `src/api/auth.test.ts` exercises the real Hono application: login, the hardened cookie
  attributes (`HttpOnly`, `SameSite`, `Path`, `Max-Age`, conditional `Secure`), `/auth/me`,
  logout revocation, expiry, both rate-limited and cross-origin refusals, absence of bearer
  token issuance, and public reads plus bearer writes staying available without the login
  configuration. Its logout CSRF tests pin the negative branch: a missing, wrong or
  session-foreign `X-CSRF-Token` answers `403 csrf_failed` without revoking the session or
  expiring the cookie, and a logout with no live session needs no token and answers `204`.
- `src/auth/admin-auth.test.ts` covers the session CSRF binding directly: only the token
  minted with the live session matches, empty and over-long values are refused, an unknown or
  revoked session is `session_missing`, and the session resolves to the same provider actor a
  bearer token resolves to.
- `src/api/schema-documents.test.ts` covers the public hosted-schema surface: exact bytes and
  canonical media types without authentication, `Content-Digest`/`ETag`/immutable caching,
  conditional `304`, 404 for unknown and 400 for oversized identifiers, rejection of mutation
  methods and oversized bodies, metadata/listing URLs that ignore attacker-controlled
  `Host`/`Forwarded` headers, the explicit `503` without a configured public origin, no
  provider/provenance leakage, and byte-identical content after a database reopen.
  `src/public-urls.test.ts` and `src/config.test.ts` cover canonical URL composition, SRI
  computation and origin validation (HTTPS, loopback-only HTTP, no credentials/path/query).
- `src/api/session-writes.test.ts` covers the dual transport end to end: a session creates,
  edits, versions, publishes, imports and correlates; a cookie write without its CSRF token, a
  wrong or foreign token and a cross-origin write all answer `403 csrf_failed` and write
  nothing; every protected state-changing route in the route table is checked for that refusal;
  a legacy bearer still works; an explicit invalid bearer plus a valid cookie answers `401` and
  never falls back; an explicit bearer wins over a cookie; expiry and logout revocation answer
  `401`; a session cannot mutate another provider's rulebook (`403`) or forge a provider id
  through the body; audit rows are attributed to the session's provider; public reads stay
  anonymous.
- `src/api/discovery.test.ts` verifies that issuer discovery authenticates before any
  discovery work, maps the shared bounded-fetch failures and validates its response against
  the generated contract; `src/discovery/discover.test.ts` covers the SSRF, size,
  content-type, redirect and metadata-validation controls with an offline transport.
- Run `bun run check` and `bun run openapi:check` from the repository root.

- **Capture explorer and correlation.** `src/capture/explorer.test.ts` and
  `src/api/captures.test.ts` cover the redacted-only projection, explicit evidence gaps, refusal
  of external/non-credential evidence, the required correlation token and a real
  structural-engine correlation against a seeded pinned version; `ui/src/CapturesPage.test.tsx`,
  `ui/src/CaptureDetailPage.test.tsx`, `ui/src/capture.test.ts` and `ui/e2e/captures.spec.ts`
  cover the UI, the correlation flow, axe-core scans and the responsive layout.
